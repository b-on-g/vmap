# $bog_vmap — архитектура

Визуальный конструктор сайтов на бесконечном холсте. Живой $mol внутри, настоящий
исходник на выходе, Гипер База под спиной.

Документ читают **все** молеры перед работой над модулем. Решения здесь приняты,
спорить с ними в отдельной задаче можно, молча нарушать нельзя.

---

## 1. Главная ставка

**Документ vmap это один класс `view.tree`.**

Не «модель узлов, из которой можно сгенерировать код». Именно исходник, который
редактор парсит, правит через AST и сериализует обратно. Мышь и текстовый редактор
работают с одним и тем же байт-в-байт файлом.

Из этого следует три вещи разом:

- **экспорт исходников бесплатный**, потому что источник истины и есть результат экспорта;
- **обратная совместимость с mol-кодом бесплатная**, потому что чужой `.view.tree` можно
  просто открыть в редакторе;
- **реактивность бесплатная**, потому что связи между узлами это штатные `<=` и `<=>`,
  а считает их `$mol_wire`, а не наш код.

### Почему связь «любой узел с любым» не требует машинерии

В `view.tree` всякий именованный под-вид, на какой бы глубине он ни лежал, становится
**плоским свойством корневого класса**. Хак так и называется — `upper`
(`mol/view/tree2/class/props.ts:41`): он поднимает объявление из-под `<=` / `<=>` наверх,
в список свойств класса.

Живой пример: в `hyoo/map/map.view.tree:44` узел `Track_dot` объявлен на пятом уровне
вложенности (`Main → sub → Pane → graphs → Diag1 → graphs`), но при этом является
свойством `$hyoo_map`, а не `$mol_plot_group`.

Значит калькулятор, лежащий свободно на холсте, и метка, зарытая внутрь артборда, для
компилятора соседи. Провод между ними это одна строка:

Точный синтаксис, проверенный прогоном компилятора на спайке S3:

```
	Calc $my_lib_calc            # свободная деталь: имя и класс, БЕЗ оператора
	calc_result = Calc result    # провод: оператор `=`, отдельная строка на уровне класса
	sub /
		<= Hero $mol_view sub /
			<= Price $mol_text title <= calc_result
```

В бандле из этого получается дословно:

```js
	wired_text(){ return (this.Calc().result()); }
	…
	($mol_mem(($.$my_doc.prototype), "Calc"));
```

Декоратор на деталь компилятор вешает сам, поэтому `Calc` создаётся лениво при первом
обращении и живёт мемоизированным синглтоном. DOM она не создаёт, потому что в `sub` не
входит. Ни сериализации, ни шины событий, ни подписок: потянул провод, редактор дописал
строку, `$mol_wire` пересчитал.

### Канонический вид документа — нормализованный

`$mol_view_tree2_normalize` **лоссивый**: он прогоняет `class_props`, а тот хаком `upper`
вытаскивает `<= Hero $mol_view …` из `sub` наверх, оставляя в `sub` голое `<= Hero`.

Для нас это удача, а не помеха. Нормализованный вид буквально совпадает с моделью из
начала раздела: все именованные под-виды становятся плоскими свойствами класса **в самом
тексте**, а не только в скомпилированном классе. Провод к любому узлу перестаёт зависеть
от того, как глубоко тот нарисован.

Отсюда два следствия, которые надо знать заранее.

Перестановка при этом двойная. Мало того что объявление уезжает из `sub` наверх, оно ещё
и встаёт **перед** свойствами, которые изначально были на верхнем уровне: `add_inner` для
поднятых зовётся во время обхода, а не в финальном цикле. Так что

```
	sub /
		<= Hero $mol_view sub /
			<= Price $mol_view title <= calc_result
```

становится

```
	Price $mol_view title <= calc_result
	Hero $mol_view sub / <= Price
	…
	sub / <= Hero
```

**Round-trip байт-в-байт возможен только на нормализованном исходнике**, то есть на
неподвижной точке нормализации. Главный тест модели ставится именно на нём, потому что это
и есть тот вид, в котором редактор держит документ: `tree( next )` сериализует класс
целиком при каждой записи, поэтому после первой же правки документ уже в этой форме.

**Чужой рукописный `.view.tree` при открытии будет переформатирован.** Вложенные
объявления поднимутся наверх, поведение не изменится, но диff будет большой. Обратная
совместимость по смыслу сохраняется, побайтовая — нет. Предупредить об этом в интерфейсе
на этапе 7, когда появится импорт чужих файлов.

### Три формы `<=`, из которых опасна средняя

Всё упирается в хак `upper` (`mol/view/tree2/class/props.ts:41`), на который повешены
и `<=`, и `<=>`. Он берёт первого ребёнка оператора и прогоняет **его** детей как список
значений по умолчанию:

| форма | детей у ссылки | что делает `upper` |
|---|---|---|
| `<= calc_result` | нет | чистая ссылка, ничего не объявляет |
| `<= Calc result` | есть | **объявляет свойство `Calc` со значением `result`** |
| `<= Price $mol_text` | есть, класс | объявляет под-вид, штатный случай |

Средняя строка выглядит как провод и проводом не является. Два исхода, оба скверные:

- `Calc` объявлена рядом → сборка падает с `Need an equal default values at … vs …`.
  Диагностика вводит в заблуждение, она говорит про дефолтные значения, хотя писали провод.
- не объявлена → **аудит зелёный**, в бандле мёртвый код:

```js
	Calc(){ return result; }              // голый идентификатор, ReferenceError
	Calc_result(){ return (this.Calc()); } // звено .result() исчезло бесследно
```

Второй исход и есть настоящая опасность: ломается в рантайме, только на том узле, куда
тянули провод, и только когда до него дойдут.

Причина потери звена в том, что `<=` компилируется через `call_of` (`js.ts:43`), который
обходит только прямых детей узла, то есть ровно одно колено. Цепочку собирает отдельная
ветка оператора `=` (`js.ts:155`), рекурсивно спускающаяся по детям.

### Правила провода

Проверено прогонами компилятора и рантайма на S1 и S3.

**Провод это ровно два токена: `имя = ИмяУзла свойство`.** Глубже не бывает. `deep = Card
Inner value` компилируется в `this.Card().Inner().value()`, но `upper` поднял `Inner` в
свойство **корня**, а не `Card`, поэтому в рантайме падает `this.Card(...).Inner is not a
function`. Сборка при этом зелёная.

Длинная цепочка и не нужна: вложенность обоих концов роли не играет, потому что `upper`
уже сделал их плоскими свойствами корня. Проверено на узле третьего уровня
(`sub → Card → sub → Inner`), провод `deep? = Inner value?` работает и на запись.
Это то самое, на чём стоит раздел.

**Двусторонность требует `?` на обоих концах.** Знака два, и они независимы: `?` слева
даёт параметр `next` в сигнатуре, `?` справа передаёт его в вызов.

**`=` ничего не объявляет.** Через `upper` он не проходит вовсе, отсюда отсутствие
коллизии `Need an equal default values`, но и отсутствие авто-объявления. Узел объявляют
отдельно, хоть в `sub /`, хоть свободной деталью на корне.

**`=` не мемоизируется.** `is_delegate` истинно, декоратор не выпускается. Так и правильно,
это чистый проброс без второго кэша.

### Капканы с зелёной сборкой

Все четыре собираются без единого предупреждения и ломаются потом. Инструмент провода
обязан не уметь их выпустить, и это проверяется тестом на этапе 3, а не ревью.

| строка | что в бандле | когда рванёт |
|---|---|---|
| `w <= Calc result` (`Calc` объявлена) | сборка падает | сразу, хоть честно |
| `w <= Calc result` (не объявлена) | `Calc(){ return result }` | `ReferenceError` при чтении |
| `w = Field value?` (`?` только справа) | `w(){ … value(next) }` | `ReferenceError: next` при **любом** чтении |
| `w? = Field hint` (`?` только слева) | `w(next){ … hint() }` | никогда, запись молча пропадает |
| `w = A B value` (три токена и больше) | `this.A().B().value()` | `B is not a function` в рантайме |

Последняя строка последнего столбца и есть худший случай: молчаливая потеря записи без
всякой ошибки.

**Капкан не отлавливается, а не выражается.** Тип провода в `$bog_vmap_lang` это
`{ name, node, prop, bidi? }`: поля под оператор нет вообще, поля под третий токен нет,
а `?` один флаг сразу на оба конца. Три капкана из пяти после этого невозможно записать,
не то что выпустить, и проверять их нечем, потому что проверять нечего.

Остаётся одна дыра — протащить знак или пробел внутрь токена. Её закрывает сверка токена
с группой `name` из **штатной** `$mol_view_tree2_prop_signature`. Грамматика взята та же,
которой пользуется компилятор, поэтому токен, прошедший проверку, гарантированно пройдёт и
его. Своя грамматика тут разошлась бы с компилятором на первом же исключении.

Валидация остаётся ровно там, где тип бессилен: узел провода должен быть **объявлен** в
документе, и при отказе в исходник не пишется ничего.

**`$mol_view_tree2_value_type` оператора `=` не знает** и падает на нём с
`Unknown value type`; studio затыкает это заглушкой `case '=': return ''`. Значит всякий
код, который классифицирует значение свойства — инспектор в первую очередь, — обязан
разбирать `=` сам, до вызова классификатора. Спотыкание случится на первом же узле живого
документа, потому что провод и есть `=`. Туда же `+NaN` и `±Infinity`, которые
классификатор тоже не берёт.

Дальний конец провода (есть ли у класса узла такой порт) в модели не проверяется
осознанно: это знает только `props_map` из `$bog_vmap_lib`, а тянуть модуль с сетью в
чистую модель ради одной проверки дороже пользы. На этапе 3 провод и так тянут из списка
портов, где неверного конца взять неоткуда.

## 2. Что берём из `$hyoo_studio`

[studio.hyoo.ru](https://studio.hyoo.ru/) это визуальный редактор одного $mol-компонента,
работающий в проде. Половина нашего фундамента там уже написана и обкатана. Забираем не
идеи, а код. Репозиторий `hyoo-ru/studio.hyoo.ru`, пак `studio` в `hyoo/hyoo.meta.tree:51`.

| Оттуда | Что закрывает |
|---|---|
| `component/component.ts` | модель узла: текст как истина, `tree()` как производная, `prop_tree()`, `prop_add`, `prop_drop` |
| `property/property.ts` | свойство и его сигнатура: `name`, `key` (`*`), `next` (`?`) через `$mol_view_tree2_prop_signature` |
| `library/library.ts` + `studio.view.ts` `library()` | палитра из любого задеплоенного пака |
| `studio.view.ts` `props_map()` | порты класса вместе с унаследованными, обходом цепочки |
| `studio.view.ts` `self_code()` | рантайм-сборка класса из трёх исходников |
| `studio.view.ts` `props_js()` / `props_css()` | нарезка JS и CSS по свойствам, гранулярность редактора кода |
| `value/bound/` | редактор биндинга, модельная сторона провода |

Три детали, до которых мы бы дошли только через грабли.

**Декораторы применяются вручную.** В строке JS, скармливаемой `new Function`, декоратор
написать нельзя. Studio дописывает `$mol_mem( $.$my_class.prototype, "prop" )` отдельными
выражениями после определения класса (`source_js_decorators()`). Без этого свойство просто
не мемоизируется, и это молчаливая поломка, а не ошибка.

**Стили только `$mol_style_attach`.** `self_code()` заканчивается вызовом
`$mol_style_attach( class_name, css )`. `$mol_style_define` тут применять нельзя, он бы
перетёр стили донорского класса.

**`predef` для `$mol_view`.** Собственные свойства `$mol_view` (`sub`, `attr`, `style`,
`event`, `field`, `dom_name`, `title`) в `web.view.tree` не попадают, потому что `$mol_view`
написан на TS. Studio дописывает их строкой-заглушкой перед парсингом (`library()`).
Копировать дословно, иначе палитра теряет базовые порты.

### Чего из studio НЕ берём

`self_code()` начинается со строки `$.$mol_wire_auto = parent.$mol_wire_auto`, то есть
превью делит планировщик реактивности с родителем и лезет в `parent`. Это требует
same-origin и убивает всякую изоляцию.

Нам это не нужно, и выяснилось, что не нужно даже без изоляции. `$mol_wire_solo` берёт
`$mol_wire_auto` глобалью, а не через DI, поэтому производный `$` наследует планировщик
сам. На S1 строку выкинули, и критерий реактивности всё равно прошёл.

Весь документ компилируется внутри сцены целиком, поэтому вся его реактивность внутренняя.
Инспекция wire-графа, ради которой studio туда и лезет, у нас идёт через мост.

## 3. Рантайм-компиляция

Компилятор `view.tree` целиком браузерный, node-зависимостей в нём нет:

```
$mol_tree2_from_string( src )        →  AST
$mol_view_tree2_to_text( ast )       →  ДЕРЕВО текста     (mol/view/tree2/to/text/text.ts:2)
$mol_tree2_text_to_string( … )       →  строка JS
new Function( '$', js )( sandbox )   →  живые классы
```

`to_text` вопреки имени отдаёт `$mol_tree2`, а не строку, и скормить его `new Function`
напрямую нельзя. Шаг `$mol_tree2_text_to_string` обязателен.

На выходе код вида `$['$my_page'] = class $my_page extends $['$mol_view'] {…}`, то есть
классы регистрируются в переданном объекте `$`. Передаём производный: `Object.create( $ )`
с добавленным `$.$ = $`. Инстанс создаём через `Class.make({ $: sandbox })`.

Компонент собирается из **трёх** исходников, как в studio: декларация `view.tree`, тело
класса на JS, стили. Порядок сборки в `self_code()`.

> `$mol_ambient` устарел, DI работает только через `this.$.X`. Классы, попавшие в
> производный `$`, разрешаются штатно, потому что цепочка прототипов ведёт к базовому.

### Класс нельзя класть в ячейку голым

Ячейка **клеймит** значение, которым владеет, и на классе это клеймо ломает тег элемента.

`$mol_wire_atom.put` на новое значение зовёт `$mol_owning_catch`, и при согласии тут же
пишет в него метку атома (`mol/wire/atom/atom.ts:171-176`, дословно то же в
`mol/wire/task/task.ts:74`, то есть `@$mol_action` ведёт себя так же).

Класс под это подпадает, хотя выглядит так, будто не должен. `$mol_owning_allow`
(`mol/owning/owning.ts:12`) пропускает и функции тоже, а единственный оставшийся фильтр
это наличие `destructor`. У `$mol_object2` есть `static destructor() { }`, статика
наследуется, значит **любой класс, наследующий `$mol_object2`, владеем** — то есть все
скомпилированные классы документа.

Дальше метка доезжает до DOM. `$mol_object2.static toString()` отдаёт
`this[Symbol.toStringTag]` **раньше** настоящего имени, а `dom_name()` это
`$mol_dom_qname( this.constructor.toString() ) || 'div'` (`mol/view/view/view.tsx:109`).
Метка вида `$bog_vmap_scene.Root<0>.build<>` превращается в тег
`<bog_vmap_scenerootbuild>`. Ошибки нет, аудит зелёный, последствия те же, что от
анонимного класса: теряется кастомный тег, а с ним и CSS по имени элемента. И `dom_name()`
помечен `@$mol_memo.method`, поэтому порча залипает на экземпляре навсегда.

Бьёт при трёх условиях сразу: значение это класс от `$mol_object2`, ячейка реально сменила
значение (ветка владения живёт внутри `if( next !== prev )`), и класс ещё никем не владеем.
Последнее даёт скверное свойство: клеймит **первая** ячейка, которая класс вернула, поэтому
симптом зависит от порядка запуска и на разных путях проявляется по-разному.

**Живыми классы держит песочница**, а не ячейка. Они лежат её свойствами, песочницу
возвращает `sandbox()`, и пока жива та ячейка — достижимы и классы. Отдавать класс из
ячейки отдельно не нужно, а вредно. Уничтожения при этом бояться нечего и в принципе:
даже попав во владение, класс от `destructor()` не пострадает, потому что
`$mol_object2.static destructor()` пустой. Цена возврата это только клеймо, пользы никакой.

**Решение**, когда класс всё же надо отдать наружу: возвращать объектный литерал
`{ Root: Klass }`. У POJO нет
`destructor`, `$mol_owning_allow` его отвергает, клеймо не ставится. Реактивность не
страдает: `$mol_compare_deep` уходит в `compare_pojo` и сравнивает поле через `Object.is`,
так что «тот же класс» даёт равенство и подписчиков не будит. На этом же держится
сохранение живого экземпляра при неудачной пересборке.

**Песочница живёт одна на документ, классы перезаписываются в ней на месте.** Пересоздавать
`Object.create( $ )` на каждой сборке **нельзя**: `$mol_object2.$` кэшируется в
`[$mol_ambient_ref]` при первом чтении и больше не меняется. Новая песочница отрезала бы
уже созданные экземпляры от новых классов, причём молча, без всякой ошибки.

При соблюдении этого правила ссылки «класс на класс» чинятся сами: генератор пишет
`new this.$['$other']()`, то есть имя разрешается в момент вызова, а не в момент
определения класса.

Класс в `globalThis` при этом не протекает, проверено на S1: собственные ключи песочницы
после сборки это ровно `["$", "<класс>"]`.

**Стили из песочницы утекают.** `$mol_style_attach` вешает `<style id="$mol_style_attach:$имя">`
в `head`, и оттуда его никто не снимает. Переименовал класс, и старый элемент остался
навсегда рядом с новым. При редактировании это счёт на сотни за сессию.

**Требование к сцене:** снимать style-элементы предыдущей компиляции перед следующей.
Отдельной задачей, а не «когда-нибудь».

### Класс обязан быть именованным

`class X extends $["X"]`, никогда `class extends $["X"]`. Замерено на S1:

| | именованный | анонимный |
|---|---|---|
| `dom_name()` корня | `z_demo` | **`div`** |
| `attr_static` под-вида | `z_demo_echo` | **`_echo`** плюс `z_demo_echo` |

`dom_name` берётся из `$mol_dom_qname( this.constructor.toString() )` через
`$mol_func_name`, у безымянного класса он пустой и падает в фолбэк `div`. Кастомный тег
теряется, а с ним и CSS по имени элемента.

Хуже второе. `view_names_owned()` клеит `$mol_func_name(Class) + '_echo'` и от безымянного
класса выдаёт голый `_echo`, одинаковый у всех анонимно скомпилированных классов. Это
коллизия между документами: чужой `[_echo]` в CSS покрасит соседний.

Восстановить имя нельзя: `$mol_func_name` при пустом `name` перебирает `for (let key in this)`
по статическому `$` класса, унаследованному от `$mol_object2.$` = `globalThis`, а наш класс
живёт только в производном `$`. Скан проходит впустую по всему `globalThis` и кэшируется
в `WeakSet`, то есть один бесплодный проход на класс, навсегда. Чем изолированнее контекст,
тем надёжнее не сработает.

### Имя класса и CSS передавать данными

Studio пишет `$mol_style_attach(${class_name}, \`${css}\`)`, и это работает лишь потому,
что классы там глобальные, а CSS не содержит бэктиков. Пользовательский CSS с бэктиком
или с `${` порвёт сборку строки.

На обоих концах `JSON.stringify`: имя уходит строкой, CSS экранированным литералом.

### Пересборка: подмена прототипа с ретаргетом атомов

Решено спайком S2, из четырёх стратегий выбрана та, которой в исходном списке не было.

Ячейка `@$mol_mem` лежит **собственным полем экземпляра** (`host[ name + '()' ]`,
`mol/wire/atom/atom.ts:24`), поэтому `Object.setPrototypeOf` не трогает ни значений, ни
подписок, ни DOM-узла. Но голая подмена прототипа правку кода **не применяет вообще**:
фибра запоминает реализацию в конструкторе (`readonly task`, `mol/wire/fiber/fiber.ts:93`).

Лечится тем, что декоратор оставляет исходник на обёртке
(`Object.assign( descr2.value, { orig } )`, `mol/wire/solo/solo.ts:34`). Алгоритм:
подменить прототип, переставить `task` на новую реализацию, вызвать `refresh()` только
там, где `String(task)` разошёлся.

Замеры на 29 свойствах и ~108 узлах DOM, полный раунд с рендером, среднее по 20 правкам:

| | 40 абзацев | 300 абзацев |
|---|---|---|
| подмена прототипа с ретаргетом | **6.1 мс** | **6.4 мс** |
| снапшот и восстановление | 9.5 мс | 15.7 мс |
| пересоздание начисто | 8.7 мс | 15.2 мс |

Сама подмена бесплатна у всех трёх, разница целиком в рендере. Выбранная стратегия
единственная не растёт с размером компонента, потому что не строит DOM заново.

Ячейки одинаково сохраняют и снапшот, и подмена. Решает то, что **в ячейку не попадает**:
каретка, фокус, позиция прокрутки, содержимое `<canvas>` и `<video>`. Снапшот теряет всё
это вместе с DOM-узлом, а заодно не умеет снимать нескалярные значения и при заливке
назад **повторно выполняет побочный эффект** сеттера.

**Четыре случая, где стратегия не работает:**

1. **Немемоизированное свойство невидимо.** Нет ячейки, нет подписчиков, будить нечего:
   метод вернёт новое значение, а в DOM останется старое. Отсюда жёсткое требование ниже.
2. **`prop` ⇄ `prop*`** теряет значение неизбежно, соло-значение некуда положить в словарь.
   Перед сносом атому нужен `emit()`, иначе зависимые молча остаются со старым кэшем.
3. **Смена базового класса**: состояние цело, но DOM-узел хранит `attr_static()` старой
   базы. Требует отката на пересоздание, определяется сравнением
   `$mol_view_tree2_class_super`.
3a. **Загрузка донорского пака.** У живого экземпляра **молча пропадает песочница**:
   `$mol_ambient_ref` это `Symbol(…)`, свой у каждого бандла, а геттер `$mol_object2.get $()`
   читает его поздним связыванием. Контекст, положенный под прежний символ, становится
   недостижим, геттер пересчитывает и падает в `globalThis`. Замер: до загрузки
   `inst.$ === sandbox()`, после — `inst.$ === window`, при том же экземпляре, живом DOM и
   нулевом канале ошибок. Стрельнёт на первом же `this.$.$мой_класс` в пользовательском
   коде. Экземпляр после смены пака выбрасывать и компилировать заново, прототипы не
   подменять.
4. **Многоклассовый документ**, то есть наш основной режим. Разобран ниже.

### Многоклассовый документ

Перезаписи классов в песочнице достаточно для **связей**, но не для **экземпляров**:
объект класса `B`, лежащий в ячейке объекта `A`, построен от старого прототипа `B` и про
перезапись `$['$B']` ничего не знает. Ему нужен свой ретаргет, такой же, как корню.
Обход дерева обязателен.

**Обходить по `sub()` нельзя**, и сразу по трём причинам:

- свободные детали в `sub` не входят по определению, то есть обход пропустит ровно ту
  сущность, ради которой затеян раздел 1;
- `sub()` у сгенерированного класса не мемоизирован (генератор декорирует только
  `next`-свойства и фабрики под-видов), поэтому вызов во время подмены выполнит
  пользовательский код и может **создать** детей, которых ещё нет;
- под-вид, временно отсутствующий в `sub`, остаётся живым экземпляром.

Обходить надо **кэши атомов**: перебрать собственные поля экземпляра, взять `atom.result()`,
рекурсивно спуститься. Ключевые дети лежат там же в `Map`.

**Объявления классов нужно топологически отсортировать перед компиляцией.**
`class $A extends $['$B']` вычисляет базу в момент определения, а
`$mol_view_tree2_to_js` идёт `for( const klass of descr.kids )` в порядке объявления и не
сортирует. Если `$A` объявлен раньше своей базы `$B`, то за один проход `new Function`
он унаследует **предыдущую** версию `$B`.

Подтверждено нагруженной проверкой на этапе 1: без сортировки тот же исходник даёт
`TypeError: Class extends value undefined is not a constructor`. Сортировку делает **сцена**,
а не хост: только она знает полный набор классов, уезжающих в один `new Function`, потому
что к классам документа добавятся классы подключённых библиотек.

**Рукописные тела применяются вперемешку с объявлениями, класс за классом.** Сначала
объявление класса, сразу за ним его обёртка с рукописным телом и декораторами, и только
потом следующий класс.

Порядок «сгенерить все объявления, потом обернуть все тела» выглядит опрятнее и **молча
неверен**: обёртка это новый класс, поэтому наследник, созданный до того, как обернули его
базу, остаётся с необёрнутой базой и теряет её рукописные методы. Ошибка не диагностируется
ничем, просто половина поведения базы исчезает.

**Требование, вытекающее из случая 1:** редактор генерирует тело класса сам и обязан
класть **каждое** свойство под `@$mol_mem` отдельными выражениями после `class`, приёмом
`source_js_decorators()`. Это не оптимизация, а условие работоспособности горячей правки.

## 4. Граница безопасности

Пользовательский код исполняется **только внутри sandbox-iframe**, начиная с первого дня.
Ретрофитить границу позже означает переписать весь рендер, поэтому она закладывается сразу.

Берём `$mol_frame` и подкласс с добавленным атрибутом. **Порядок ключей критичен**,
`sandbox` обязан стоять ДО `^`:

```
$bog_vmap_app_pane_frame $mol_frame
	attr *
		sandbox \allow-scripts
		^
		src null
```

Кадр объявлен в `app/pane/`, а не рядом со сценой: он принадлежит хосту, а `app/frame/`
по разделу 7 занят артбордом.

Обратный порядок даёт **полностью незапесоченный кадр при внешне правильном атрибуте**.
`$mol_dom_render_attributes` (`mol/dom/render/attributes/attributes.ts:8`) идёт
`for( let name in attrs )`, то есть в порядке вставки ключей. Форма с `^` наверху
компилируется в `{ ...super.attr(), sandbox: … }`, поэтому первым выставляется источник
кадра, браузер немедленно начинает загрузку, а приехавший следом `sandbox` к уже начатой
не применяется. Атрибут в DOM при этом есть, аудит зелёный, изоляции нет.
В бандле должно получиться ровно `{"sandbox":"allow-scripts", ...super.attr(), "src":null}`,
и это единственная проверка, которую видно глазами в собранном коде.

### У кадра нет адреса: он поднимается разметкой

**Во всём проекте ровно одна страница — `app/index.html`.** У сцены своей нет, и это не
экономия, а следствие: страница сцены была бы вторым адресом приложения, а у нас PWA.
Кадр получает **разметку**, а не ссылку: `srcdoc` вместо `src`.

Граница от этого не страдает ни на йоту. **Изоляцию даёт `sandbox`, а не происхождение
документа:** `allow-scripts` без `allow-same-origin` выдаёт кадру уникальный opaque origin
независимо от того, приехал документ по ссылке или разметкой. Всё, что сказано ниже про
`self.origin`, `localStorage`, `parent` и отдельный `globalThis`, остаётся дословно верным.

Что разметка обязана нести:

- корневой узел `$bog_vmap_scene` и тег скрипта на бандл сцены **абсолютным** адресом.
  В opaque origin относительный путь резолвить не от чего. Кросс-origin `<script src>`
  внутри границы работает и замерен ниже, отдельного разрешения песочнице не нужно;
- инлайновый `color-scheme: dark`. Без него Chrome держит прозрачный кадр прозрачным
  только до тех пор, пока что-нибудь внутри не поднимет слой композиции — трансформ
  камеры на `Stage` его поднимает, — и с этого момента заливает кадр своей бледной
  подложкой. Замерено в живом окне с тикающим `requestAnimationFrame`, не под
  автоматизацией. Кадр непрозрачен намеренно, поэтому всё, что должно быть видно под
  документом, живёт внутри него: сетка холста рисуется там же. Инлайном, а не правилом,
  чтобы держалось и на первой отрисовке, до загрузки бандла;
- `src` не выставляется вовсе, и именно **снимается**, а не обнуляется строкой: кадр с
  пустым `src` грузит страницу, на которой стоит. `null` в словаре атрибутов — это
  `removeAttribute`.

Разметку строит сам пейн (`scene_html()`), потому что кадр его. Имя корневого класса
склеено из двух половин, иначе граф зависимостей MAM нашёл бы его в строковом литерале и
затащил бы весь бандл сцены внутрь бандла редактора.

**Проверять наличие атрибута бесполезно.** Проверять надо `self.origin` изнутри кадра: у
запесоченного он строка `"null"`.

**Именно `self.origin`, а не `location.origin`.** Второй возвращает origin URL-а, а не
документа, и в запесоченном кадре честно отдаёт `http://localhost:9080`. Проверка по нему
всегда зелёная и ничего не значит. Косвенный признак в логах — `blob:null/…` в ссылках,
созданных внутри сцены.

**Кросс-origin `<script src>` внутри границы работает**, отдельного разрешения песочнице
не нужно: замерено загрузкой `https://mol.hyoo.ru/web.js` в кадр с `allow-scripts` без
`allow-same-origin` — 463 мс, 812 глобалей `$mol_*`, при том что `localStorage` и
`parent.location` в том же кадре дают `SecurityError`.

`allow-scripts` **без** `allow-same-origin` даёт iframe уникальный opaque origin даже при
загрузке с собственного домена. Это работает на gh-pages, где отдельный origin взять негде.
Внутри нет доступа ни к `localStorage` хоста, ни к его IndexedDB, ни к `parent`, только
`postMessage`.

Совмещать `allow-scripts` с `allow-same-origin` для недоверенного контента **нельзя**:
такая пара снимает изоляцию полностью.

### Граница даёт ещё и отдельный реактивный граф

Выяснилось на S1 и оказалось вторым, независимым основанием для iframe.

Указатель на текущую фибру это `$mol_wire_auto_sub`, объявленный как `export let` в
`namespace $`, то есть обычное свойство `$`. А `$` в web-сборке равен `globalThis`
документа. Отсюда:

- **отдельный origin означает свой `globalThis`, а значит полностью независимый
  планировщик.** Строка studio `$.$mol_wire_auto = parent.$mol_wire_auto` существует ровно
  затем, чтобы графы **склеить**, то есть по умолчанию они раздельные;
- **внутри одного документа своего планировщика не получить в принципе.**
  `Object.create( $ )` не спасает: функция пишет в `$` своего модуля, а не в `this`.

Практическое следствие важнее теоретического. Без границы зациклившаяся или подвисшая
фибра пользовательского кода морозит фибры редактора, и это не гипотеза, а неизбежность
общего планировщика. С границей сцена может встать колом, а редактор продолжит работать.

Цена та же, что уже названа: хост не может ни `$mol_wire_sync` через границу, ни
посмотреть граф сцены. Только мост.

**Граница проходит между сценой и хостом, а НЕ между документом и сценой.** Документ живёт
в том же `globalThis`, что и сцена, поэтому граф у них общий: замерено, что `report_task`
сцены читает `dom_final()` документа и честно от него просыпается. Значит **зациклившаяся
фибра пользовательского кода морозит всю сцену целиком**, включая обработку моста.
Редактор при этом жив, и это ровно то, что обещано выше, — но хосту нужен признак
залипшей сцены и способ её перезагрузить, иначе пользователь увидит мёртвый холст без
объяснений. Отдельного графа у документа нет и по этой архитектуре не будет.

### Два бандла в одном документе: что переживает, а что нет

Замерено на спайке S4 загрузкой `mol.hyoo.ru/web.js` поверх работающей сцены.

**Правило связывания.** Обращение к чужому модулю **из тела метода** позднее, и достаётся
оно последнему загруженному. Обращение к классу **своего же файла**, включая `extends`,
раннее и остаётся при своей копии.

Отсюда всё остальное:

- **Планировщик не встаёт.** `$mol_wire_auto_sub` это одно свойство `globalThis`, и обе
  копии фреймворка ходят в него поздним связыванием, то есть указатель на текущую фибру у
  них общий. А `plan()` ссылается на `$mol_wire_fiber` как на локальную переменную своего
  IIFE, поэтому старые фибры складываются в свой старый `planning` и его же разгребают.
  Два планировщика тикают рядом и сшиваются по утиной типизации.
- **Ломается `instanceof`.** `$mol_view.render()` (`view.tsx:307`) проверяет
  `child instanceof $mol_view`, где `$mol_view` — локальный класс своего файла. Документ,
  унаследованный от `$mol_view` **пака**, проверку не проходит, и ветка падает в
  `String( child )`. Компиляция при этом зелёная, ошибок по мосту нет, документ отрисован
  в собственный узел — его просто не приложили в DOM.
- **Тот же оператор в двух файлах ведёт себя противоположно**, и это самое коварное.
  `kid instanceof $mol_view` внутри `scene.view.ts` связывается поздно, потому что
  локального объявления там нет, и достаётся паковому классу — работает, `sizes_of`
  из-за этого цел. Он же внутри `view.tsx` берёт локальный класс файла — не работает.
  Смотреть надо не на выражение, а на то, объявлен ли класс в этом же файле.

- **Графы сшиваются между копиями** по утиной типизации: паковый атом, прочитанный из
  фибры сцены, честно подписывает её на себя. Реактивность через границу копий живая.
  `instanceof` ломается ровно потому, что он единственный сравнивает **идентичность**
  класса, а не форму объекта.

**CSS пака приезжает ПОСЛЕ нашего и выигрывает ничьи.** Сцена вешает свой style-элемент
в `css_attach()` до того, как загрузится `web.js` пака, поэтому все паковые правила стоят
в `head` ниже наших. При равной специфичности решает порядок, и решает не в нашу пользу.

Поймано на расстановке: `[mol_string]` из пака объявляет `position: relative`, наш
однократный атрибутный селектор имел ту же специфичность и проиграл. Узел прочитал `left`
как сдвиг от статической позиции и уехал на ширину соседа. Два других узла легли верно
**случайно** — у их классов `position` в паке не объявлен.

Значит всякое правило, которое сцена пишет про узлы, отрисованные паком, обязано выигрывать
**объявлением**, а не позицией: выше специфичность плюс `!important`. Порядок правил чужого
пака мы не назначаем и назначить не можем.

Цифры пака `mol.hyoo.ru/web.js`: 2.25 МБ, **610 мс вхолодную**, 142 мс из кэша. Первая
загрузка палитры заметна, это надо будет прикрыть в интерфейсе. Стилей в `head` после
загрузки 177, из них наш ровно один — уборка стилей прошлой компиляции продолжает работать,
префиксы не пересекаются.

**Монтировать документ узлом, а не под-видом:** `[ this.instance().dom_tree() ]` вместо
`[ this.instance() ]`.

#### Остальные `instanceof` на границе

Через границу в сцену приезжает ровно одно — экземпляр документа и его дети. Обратно
ничего, сцена своих видов в документ не отдаёт. Поэтому список короткий, и он прогнан.

**Ломается молча, замерено:** `view_names_owned()` (`view.tsx:369`) проверяет
`owner?.host instanceof $mol_view`, а хозяин корня документа — вид **сцены**, для паковой
копии чужой. Следствие: селектор `[bog_vmap_scene_instance]` на корень документа молча
перестаёт работать после загрузки пака. Нам это скорее на руку, стили сцены и не должны
течь в документ, но правило, написанное в расчёте на него, не сработает.

**Прочитано, не воспроизведено:** `$mol_wire_atom.resync()` (`atom.ts:105`) проверяет
`pub instanceof $mol_wire_task`, чтобы прибить подвисшие задачи. Связывание позднее,
задачи у сценового атома сценовые, значит `destructor()` им не позовётся. Ошибки не будет,
будет невыключённая задача. Сцена ходит через `$mol_wire_async`, так что путь достижим.

**Ограничение на будущее:** `Stage` нельзя заворачивать в `$mol_scroll` или `$mol_list`.
`view_find()`, `force_render()` и `$mol_list.render_visible` тоже сравнивают виды, а при
монтировании узлом `$mol_list` не промолчит, а упадёт на `el.minimal_height is not a
function`: `?.` спасает от `null`, а не от `Element`.

**Проверено безопасным, перепроверять не нужно:** `$mol_compare_deep` (`deep.ts:22`)
сравнивает прототипы первым делом, поэтому ложного равенства между копиями не бывает
(важно, через него идёт каждая запись в ячейку); `$mol_owning_allow` (`owning.ts:13`) —
оба конца связываются поздно; `plugin instanceof $mol_plugin` и `view_classes()` границу
не пересекают вовсе.

`Stage().minimal_height()` при монтировании узлом становится нулём, но после загрузки пака
он был бы нулём и без правки. Culling это не задевает: его делает **хост** по `sizes`,
которые приезжают отдельным сообщением. `dom_tree()` мемоизирован и отдаёт `Element`, а `render()` для
`Element` идёт по ветке `child instanceof Node` и прикладывает как есть. Внутренняя
реактивность документа не страдает, она целиком внутри его поддерева.

### Кто чем владеет

| | Хост (`$bog_vmap_app`) | Сцена (`$bog_vmap_scene`) |
|---|---|---|
| Текст документа | источник истины | производная копия |
| Парсер и AST | да | нет |
| Компиляция и исполнение | нет | да |
| Камера и геометрия | источник истины | получает как данные |
| Выделение, ручки, провода | да, на своём оверлее | нет |
| Гипер База, ключи, сеть | да | **нет доступа вообще** |
| Палитра, инспектор, редактор кода | да | нет |

Поток односторонний: хост правит текст, шлёт в сцену, сцена перекомпилирует. Назад идут
только измеренные размеры узлов, значения портов для инспектора и ошибки компиляции.

**`event.source` доверять нельзя, канал угоняется.** У сцены opaque origin, поэтому
сверять origin не с чем, и любое окно, способное дотянуться до хоста, может прислать
`ready` и забрать мост себе. На этапе 1 это произошло по-настоящему: посторонний
отладочный кадр перехватил канал, и хост час слал сообщения в мёртвое окно, без единой
ошибки. Личность пира берётся только из `Scene().dom_node().contentWindow` и сверяется
на каждом сообщении, для чего у `$bog_vmap_bridge_read` есть второй параметр.

**Cross-origin `Window` нельзя класть в `@$mol_mem`.** `$mol_wire_atom.put` зовёт
`$mol_compare_deep`, тот обходит объект, читает `location.href` и получает `SecurityError`.
Обработчик сообщений умирает молча, в живых остаётся только запись в `$mol_fail_log`.
Ссылку на окно держать обычным полем.

Ключевое следствие: чужой код не видит ключей пользователя, потому что сеть живёт в хосте.

### Что обязано жить на оверлее, а что может в сцене

Правило владения формулируется не «редакторская обвязка вся у хоста», а точнее:

**На оверлее хоста живёт всё, что несёт состояние или принимает ввод.** Рамка выделения,
ручки, провода — они сообщают пользователю, что выбрано, и принимают жесты, поэтому чужой
код не должен иметь к ним доступа. Это про неподделываемость, а не про эстетику.

**Чисто декоративная подложка может жить в сцене.** Сетка не сообщает состояния и ввода не
принимает; если из-за компоновки кадра ей там место — пусть будет там. Камера у сцены уже
есть, она приезжает `camera_set`-ом.

**Таблица владения — про власть над документом и состоянием редактирования**, а не про то,
кто оптимизирует отрисовку. Поэтому **culling делает сцена**: у неё уже есть расстановка,
камера и собственный вьюпорт, и при пане не летит ни одного сообщения. Обратный путь, где
видимое множество считает хост и шлёт списком, породил бы трафик на каждое движение
камеры — против того, ради чего пак уехал в URL, а сторож сделан по ожиданию.

Два инварианта, без которых culling становится источником багов:

- **меняется то, что рисуется, и никогда то, что хранится.** Пан не смеет изменить исходник
  документа ни на байт; проверяется тестом «пан туда-обратно, текст посимвольно тот же»;
- **хост не забывает габариты скрытых узлов.** Сцена измеряет только отрисованное, и если
  хост просто примет новый `sizes`, рамка выделения на узле, ушедшем за край, мигнёт или
  исчезнет. Последний известный габарит держать, пока узел не удалён из документа.

Совсем плохой путь, названный и отвергнутый: фильтровать `sub` в пушимом исходнике. Это
полная перекомпиляция документа на каждый кадр пана, дороже всего, что culling экономит.

Три правила самого предиката, каждое поймано разбором, а не отладкой:

- **неизвестное показывается.** Узел, о котором ничего не известно, скрыть нельзя: он
  никогда не отрисуется, никогда не будет измерен и никогда не перестанет быть неизвестным;
- **размещение важнее последнего измерения.** Сразу после перетаскивания хост уже сдвинул
  деталь, а последний замер описывает, где она была. Судить по устаревшему началу координат
  значит гасить узел ровно в тот момент, когда его тащат через край;
- **перекрытие телом, а не точкой**, иначе деталь с углом за экраном и корпусом на экране
  пропадает.

**Фильтр ставится собственным свойством `sub` на экземпляре, а не классом-обёрткой при
компиляции.** Два следствия. Компиляция остаётся ровно тем, что сказал документ. И подмена
прототипа из задачи 4.3 собственных свойств не трогает, поэтому фильтр переживает пересборку
вместо того, чтобы вписываться в неё заново. Прототип при этом искать **в момент вызова**:
захваченный `sub` после подмены оказался бы предыдущей реализацией, и холст рисовал бы
старый документ, пока остальные свойства следуют за новым.

### Один экран без режимов

Оверлей хоста лежит прозрачным слоем поверх iframe и ловит **все** указательные события,
всегда: пан, зум, перенос детали, дроп из палитры, выделение. Переключателя «Правка/Запуск»
нет с 05.09.2026, вместо него три вещи.

- **Клик без движения** (нажатие и отпускание со сдвигом не больше 4 экранных px) хост
  и выделяет узел по известным габаритам, и шлёт в сцену `click_at` с точкой в мировых
  координатах и модификаторами. Сцена находит элемент `elementFromPoint`, поднимается до
  ближайшего фокусируемого (`tabIndex >= 0` или `isContentEditable`), даёт ему `focus()` и
  диспатчит синтетические `pointerdown`, `pointerup`, `click` с `bubbles: true`. Дальше
  клавиатура идёт в кадр сама. Сцена отвечает на `click_at` немедленным `sizes`: клик —
  самое вероятное место зациклиться коду документа, и молчание после него сторож обязан
  заметить, а не списать на «ничего не изменилось».
- **Дыра под выделенным узлом.** Пока узел выделен, оверлей прорезан инлайн-стилем
  `clip-path: polygon(evenodd, …)` по экранному прямоугольнику узла, и внутри него iframe —
  верхний слой страницы: hover, скролл, выделение текста, перетаскивание внутри компонента
  идут ему по-настоящему. Рамка и угловые ручки рисуются вокруг дыры, на оверлее; полоса в
  8 экранных px вокруг бокса считается попаданием в узел на любом зуме, за неё узел и
  переносится. Ключ `clipPath` в словаре стиля присутствует всегда (`none`, когда ничего не
  выделено): `$mol_dom_render_styles` не снимает исчезнувшие ключи. Дыра закрывается на
  время переноса из палитры: у того жеста нет захвата указателя, и отпускание над дырой
  ушло бы в кадр, а хост не узнал бы о дропе.
- **Пульс сторожа идёт всегда**, начиная с первого `sizes`. Слепая зона прежняя — код
  документа завис на событии, которого хост не посылал, — только теперь такое событие
  приходит сквозь дыру, а не в «Запуске».

**Осознанное ограничение:** hover-состояния невыделенных компонентов не работают, события
до них не доходят. Это цена того, что состояние и ввод редактора живут на оверлее и
документ не может их подделать.

Не замерено в браузере, утверждается по спецификации: `clip-path` на нетрансформированном
оверлее не меняет containing block и не конфликтует с единственным `transform` системы,
который стоит на `Stage` внутри сцены; `element.focus()` внутри запесоченного кадра
переводит фокус в кадр.

## 5. Библиотеки компонентов

Пользователь должен собирать свои компоненты и переиспользовать их в других приложениях.
Механика для этого уже существует, придумывать нечего.

**Библиотека компонентов это задеплоенный MAM-модуль.** Сборка кладёт рядом с `web.js`
файл `web.view.tree` (`mol/build/build.node.ts:576`) — полное дерево классов бандла с их
базами и свойствами.

**Адрес: `<pack>/web.view.tree`, без `-/`.** Путь с `-/` это раскладка дев-сервера, а на
проде содержимое `-/` публикуется в корень. Замерено на двух живых паках:

| адрес | ответ |
|---|---|
| `https://mol.hyoo.ru/web.view.tree` | 200, 223 КБ |
| `https://mol.hyoo.ru/-/web.view.tree` | **404** |
| `https://b-on-g.github.io/gram/web.view.tree` | 200, 77 КБ |
| `https://b-on-g.github.io/gram/-/web.view.tree` | **404** |

То есть правильно `new URL( 'web.view.tree', pack )`, дописывать ничего не надо.

Отсюда два источника, оба сводятся к одному united-дереву:

1. **Донорский пак.** Любой URL задеплоенного $mol-приложения. По умолчанию
   `https://mol.hyoo.ru`, то есть вся стандартная библиотека сразу в палитре. Любое
   $mol-приложение в мире становится источником компонентов без нашего участия.
2. **Ленд-библиотека.** Компоненты живут в Гипер Базе исходниками (три файла на компонент).
   Публикация и подключение идут ссылкой, деплой не нужен, шарится как всё остальное в базе.

Сцена обрабатывает оба одинаково. Донорский пак приезжает готовым `web.js`,
ленд-библиотека приезжает исходниками и компилируется той же цепочкой, что и сам документ.

**Наружу источники неотличимы, и это проверяется ассертом**, а не соблюдается на слово:
тест строит обе библиотеки из одних исходников и сверяет список классов и порты. Всё, что
ниже добычи текста — разбор, заглушка `$mol_view`, нормализация, обход цепочки — общее и
от источника не зависело никогда.

Две вещи, которые оказались неочевидными:

- **ленд-библиотека это ОДИН неймспейс.** Компонент, наследующий соседний компонент той же
  библиотеки, резолвится только потому, что исходники склеиваются в один текст **до**
  разбора. Фикстура из одного компонента этого не задела бы вовсе;
- **наружу классы отдаются без заглушки `$mol_view`**, иначе она затенила бы настоящий
  класс пака.

Схема ленд-библиотеки живёт **отдельным под-модулем**, потому что тащит в бандл всю Гипер
Базу: замерено — в бандле общей части упоминаний `giper_baza` ноль, в бандле ленда 1256.
Палитре и инспектору нужен только пак, и платить за это Базой они не должны.

### Донорский пак ровно один на кадр

Второй пак поверх первого **отравляет половину палитры без единого сигнала**. Замер:
поверх `mol.hyoo.ru` загружен `b-on-g.github.io/gram/`, и из 414 классов `$mol_*`
**277 остались с протухшей базой** — `$mol_grid`, `$mol_paginator`, `$mol_float`, все
иконки. Их редекларировал первый пак, второй такого класса не несёт, и их `$mol_view`
больше не тот, что лежит в `$`. Документ с `$mol_string` при этом работает, а
`$mol_icon_pin` рисуется строкой при зелёной компиляции и пустом канале ошибок.

**Смена пака означает новый кадр сцены.** Ленд-библиотеки под ограничение не
попадают: они компилируются исходниками в ту же песочницу и наследуются от текущего
`$['$mol_view']`.

### Пак приезжает сообщением, а держит правило поколение кадра

Адрес пака ехал в `?pack=` кадра, и держало правило то, что браузер сам перезагружал кадр
на смену `src`. Адреса у кадра больше нет — раздел 4, — поэтому пак едет вниз сообщением
`pack_set`, а правило держит **ключ кадра**.

Запрет «сообщением слать нельзя» снят не потому, что прежний замер неверен. Он верен:
второй пак поверх первого по-прежнему отравляет 277 классов из 414 молча, и сцена
по-прежнему не умеет выгрузить бандл. Изменилось другое — **у кадра появилось поколение**.
Адрес пака входит в ключ `Scene*`, а ключ у `@$mol_mem_key` это тождество экземпляра:
другой пак это другой `$mol_frame`, другой узел и другой документ. Сцена, которой назвали
пак, ни разу в жизни не видела предыдущего. Ту же механику давно использует кнопка
«Перезагрузить сцену», она только бампает число в том же ключе.

Три следствия, каждое проверено тестом:

- **пак уходит первым**, до документа и библиотек. Сцена **ничего не компилирует**, пока
  пак не назван: класс выбирает базу один раз, и документ, собранный на миллисекунду
  раньше, навсегда унаследует `$mol_view` самой сцены. Пустой холст на время загрузки
  дешевле молча неверной базы;
- **рукопожатие считается по кадру**, а не по пейну. Иначе смена пака оставляла бы
  `handshake` больше нуля, хост слал бы в ещё не загрузившееся окно, и все эти сообщения
  терялись бы молча, а сторож считал бы загрузку пака простоем нового кадра;
- **смена лендов кадра не трогает** и трогать не должна: они компилируются в ту же
  песочницу, и перезагрузка стоила бы камеры и живого состояния компонентов.

**Адрес пака в строке запроса не едет и не поедет.** Кроме того, что адреса нет вовсе,
замерено дважды: дев-сервер вешается на запросе, где в параметре закодирована папка `-/`,
и не досчитывается за 12 секунд. Прежний довод против фрагмента (`#pack=`) тоже остаётся в
силе на будущее: смена одного лишь фрагмента это same-document navigation, документ не
трогается вовсе, а сам фрагмент у $mol занят под `$mol_state_arg`.

### Адрес пака нормализовать до слэша

`new URL( 'web.js', 'https://b-on-g.github.io/gram' )` даёт
`https://b-on-g.github.io/web.js` — последний сегмент пути отбрасывается. Со слэшем на
конце всё верно. Дефолт `https://mol.hyoo.ru` работает случайно, потому что это корень
origin, а **любой пак на gh-pages, включая все наши, без слэша адресуется мимо**.

Достраивать слэш надо в **производном** свойстве, а не в самом редактируемом поле: поле
правится руками, и нормализация внутри него дописывала бы слэш на каждом нажатии клавиши,
так что адрес нельзя было бы досочинить до конца. Правило общее для всех полей, которые
человек набирает: введённое хранится как есть, приводится только производное.

Обход существует и проверен — подмена `Symbol.hasInstance` на каждой копии `$mol_view` —
но это патч чужого фреймворка глобально и ослабление проверки, на которой стоят
`view_classes()` и плагины. Держим в кармане, не закладываемся: смешение **версий одного
класса** из двух паков он всё равно не лечит.

Порты любого класса, включая унаследованные, даёт обход цепочки наследования по
united-дереву (`props_map` в studio).

**Круг замыкается на экспорте.** Выгруженный документ это MAM-модуль, а MAM-модуль после
деплоя это донорский пак. То есть любой собранный в vmap сайт автоматически становится
библиотекой компонентов для следующего.

Это не рассуждение: проверено на постороннем приложении, не имеющем к vmap отношения.
`https://b-on-g.github.io/gram/` отдаёт 159 классов, из них 8 собственных
(`$bog_gram`, `$bog_gram_chat`, `$bog_gram_field`, `$bog_gram_avatar` и далее), цепочка
`$bog_gram → $mol_book2 → $mol_scroll → $mol_view → $mol_object`, 431 порт с учётом
унаследованных. Любое задеплоенное $mol-приложение уже является библиотекой, включая наши
собственные, и делать для этого ничего не нужно.

## 6. Файлы

Требование: загружать файлы в пространство, делиться ими, использовать в приложениях.

**Ассет это отдельный blob-ленд Гипер Базы**: байты плюс имя и MIME-тип, то есть готовый
`$giper_baza_file`. Именно отдельный ленд, а не поле документа, потому что тогда файлом
можно поделиться самостоятельной ссылкой и переиспользовать в разных документах.

**Поля со списком ассетов у документа НЕТ, и это осознанно.** Идентификатор в тексте и есть
линк ленда, поэтому `asset:<id>` разрешается **глобально**, через `$giper_baza_glob.Pawn`,
не обращаясь к документу вовсе. Поле понадобилось бы только чтобы ответить «какие ассеты у
этого документа», а этот ответ уже даёт разбор текста. Второе хранилище того же факта
разойдётся с текстом при первой же ручной правке в редакторе кода — тот же довод, по
которому в схеме нет проводов (раздел 9).

Следствие: правила про `remote()` в схеме и `.remote(store)` после `.ensure(null)` тут
**неприменимы**, а не «соблюдены» — поля-ссылки нет. Забота остаётся: ленд, добытый по
линку, сам не синкается, поэтому синк висит на пути чтения файла.

Правила из практики, нарушение которых стоит суток отладки:

- запись blob и заведение нового ленда **только из фибры**, иначе вечный PoW-ретрай;
- авто-синк blob-лендов делается override `remote()` **в схеме**, не во вьюхе;
- `atom_link_to` требует `.remote(store)` после `.ensure(null)`, иначе file pawn не пушится.

### Схема `asset:` и кто её подменяет

В документе ассет адресуется устойчивым идентификатором: `uri \asset:7f3a…`. Подменяет
его тот, кто рендерит.

- **Сцена** подменяет на `blob:` непосредственно перед компиляцией, текстовой заменой.
- **Экспорт** подменяет на относительный путь `./assets/<name>` и кладёт файл в модуль.

Документ при этом хранит один и тот же id, и ни сцена, ни экспорт не пишут обратно.

Байты доезжают до сцены **по мосту**, а не по URL. `blob:`-ссылка, созданная хостом,
привязана к его origin и в opaque-origin песочнице не откроется. `postMessage` передаёт
`ArrayBuffer` через structured clone, в том числе transferable, сцена сама зовёт
`URL.createObjectURL`. Доставка ленивая: сцена просит ассет по id, когда он реально
понадобился.

## 7. Раскладка модулей

Корень `bog/vmap/` держит **только** `vmap.meta.tree` и документацию, без кода. Причина
в том, что `$bog_vmap_scene` тащит родительскую папку `bog/vmap/` в граф зависимостей, и
если положить редактор в корень, он уедет в бандл сцены. Приложения живут в подпапках,
как у `bog/smalljs/app/` и `raggu/web/app/`.

```
bog/vmap/
├── vmap.meta.tree
├── ARCHITECTURE.md   PLAN.md
│
├── lang/       $bog_vmap_lang     AST: узел, свойство, биндинг. Порт studio, ничего не исполняет
├── lib/        $bog_vmap_lib      библиотеки: донорский пак и ленд-библиотека, united-дерево, порты
├── asset/      $bog_vmap_asset    файлы: blob-ленды, схема asset:, доставка, шаринг
├── bridge/     $bog_vmap_bridge   протокол postMessage, общий для обеих сторон
│
├── app/        $bog_vmap_app      ПРИЛОЖЕНИЕ-РЕДАКТОР (единственный index.html)
│   ├── pane/                      камера, оверлей, culling
│   ├── frame/                     артборд
│   ├── card/                      свободная деталь на холсте
│   ├── wire/                      провода поверх сцены
│   ├── code/                      редактор кода узла
│   ├── palette/                   палитра
│   ├── inspect/                   инспектор свойств
│   ├── doc/                       схема Гипер Базы и операции над документом
│   └── export/                    выгрузка MAM-модуля
│
├── part/       $bog_vmap_part     пак деталей: палитра по умолчанию, страницы нет
└── scene/      $bog_vmap_scene    ПРИЛОЖЕНИЕ-ПЕСОЧНИЦА, страницы нет
```

Реестра классов в сцене больше нет. Компоненты приезжают донорским паком по URL, поэтому
в бандл сцены их зашивать не требуется.

**Страница в проекте одна, `app/index.html`.** Ни сцене, ни паку деталей страница не
нужна: сцену поднимает разметка кадра тегом скрипта на её `web.js` (раздел 4), а от пака
редактору нужны `web.js` и `web.view.tree`. Сборке страница тоже не нужна — `-/index.html`
пишется, только если исходная есть, а `-/test.html` генерится в любом случае, так что
`-/test.html` каждого модуля жив.

Раскладка деплоя из этого следует прямо: **редактор публикуется в корень сайта**, а
остальные модули папками под ним.

| | |
|---|---|
| `https://b-on-g.github.io/vmap/` | редактор, единственная страница |
| `…/vmap/scene/web.js` | бандл песочницы, его тянет разметка кадра |
| `…/vmap/part/web.view.tree` | дерево классов пака, его читает палитра |

Обе раскладки, дев-сервер и деплой, выводит одна чистая функция `$bog_vmap_lib_sibling`.
Признак прежний — хвостовой `-` в адресе страницы значит дев-сервер, там модули лежат
рядом, каждый в своём `-/`. Без него это деплой, и тогда сосед это папка **внутри** той,
из которой отдана страница редактора.

## 8. Холст

### Камера

`$mol_touch` берём как есть, плагином на оверлее. Он уже отдаёт `pan` (вектор) и `zoom`
(скаляр) из pointer-событий, включая пинч, и уже переводит экранные координаты в мировые
в `action_point()` (`mol/touch/touch.view.ts:62`). Хит-тестинг почти готов.

Зум изотропный, одним скаляром, как в Фигме. Двухосный `scale` из `$mol_plot_pane` не нужен.

**CSS-трансформ в системе ровно один — на сцене.** Хост камеру в трансформ не переводит:
он шлёт `camera_set`, а сетку двигает пересчётом атрибута `d` у SVG-пути. Так линии
остаются чёткими на любом зуме, толщина штриха не масштабируется, и `transition` из
`[mol_view]` в это не вмешивается, потому что `d` переходами не анимируется.

### Почему не `$mol_plot_pane`

Узлы обязаны быть настоящими компонентами с инпутами, фокусом и скроллом, а pane это
`$mol_svg_root`, заточенный под графики: авто-фит по `dimensions()` данных, раскраска по
hue, свой culling графиков (`mol/plot/pane/pane.view.ts:141`).

Сцена это **HTML-слой** под `transform: translate() scale()`, узлы позиционируются абсолютно
в мировых координатах. Из плота берём `$mol_touch` и линейки `$mol_plot_ruler` для фоновой
сетки, сам pane не берём. Идею culling копируем: `dimensions_viewport()` в
`pane.view.ts:180` даёт готовую формулу перевода вьюпорта в мировые координаты.

### Артборды и свободные детали

**Артборд** это узел документа, играющий корень страницы. Внутри артборда редактор
работает не по координатам, а **по дереву**: перетаскивание вставляет узел в `sub` родителя
на позицию, обратная связь это линия вставки между детьми. Вёрстка остаётся родным
$mol-флексом, поэтому экспорт даёт нормальный адаптивный код без `position: absolute`.

**Свободная деталь** лежит на холсте по координатам `x, y` вне артбордов. Её класс тоже
компилируется, но в `sub` артборда она не входит, а значит DOM не создаёт. Существует она
ради своих портов.

Обе сущности это свойства одного корневого класса документа, см. раздел 1.

## 9. Документ в Гипер Базе

Схема остаётся **чистой**. `static @$mol_action` на сущности ломает синхронизацию, весь
CRUD живёт во вьюхах.

Текст храним **по узлам**, отдельным `$giper_baza_atom_text` на узел
(`giper/baza/atom/atom.ts:126`; типа с именем `atom_str` не существует), а не одним
`sand_ordered` на весь документ. Причины две: `sand_ordered` теряет текст при одновременной правке и квадратичен
на запись (76 мс на правку при 500 правках). Совместное редактирование получается
по-узловое, LWW. Настоящий co-editing внутри одного узла откладываем до починки движка.

Числа держим в `atom_real`. `atom_bint` не переживает круг записи и чтения: пишешь `3000n`,
читаешь `null`.

**Аксессоры к baza-атомам — обычные методы, без `@$mol_mem`.** Ячейка на таком аксессоре
протухает **навсегда** после первой записи через неё: запись в `@$mol_mem` замораживает
зависимости, и приехавший по сети юнит её больше не будит. Замерено на двух лендах через
`units_steal`: сырой атом после мержа `BBB`, аксессор отдаёт `AAA` до конца сессии.

Для со-редактирования это худшее из возможных мест, потому что протухает **только тот узел,
который правил ты сам**. Человек правит узел, коллега правит тот же, мерж проходит верно,
а на экране у первого его собственный старый текст, без единой ошибки. Реактивность при
обычном методе не теряется: `val()` внутри поуна и так wire-ячейка.

Из-за этого же `$giper_baza_entity` не берём: его `title()` написан именно этой формой, а
переопределить обычным методом не даёт TS (TS2425). Своё поле `Title: $giper_baza_atom_text`
на `$giper_baza_dict.with` даёт тот же ключ и те же байты на проводе.

Мастеров модуль не прописывает и `masters()` не перебивает. Узел выбирает приложение.

## 10. Экспорт

Выгружается настоящий MAM-модуль, а не абстрактный «проект»:

```
<name>/
├── <name>.view.tree      документ как есть, байт-в-байт из редактора
├── <name>.view.ts        JS-логика узлов, собранная в namespace $.$$
├── <name>.view.css.ts    стили
├── <name>.meta.tree
├── assets/               файлы, ссылки asset: переписаны на относительные пути
└── index.html
```

### Превью прощает то, чего не прощает выгрузка

Расхождение, о котором надо знать заранее: **в сцене рукописное тело идёт через
`new Function`, где годится любой JS, а в экспорте оно ложится в `.view.ts` и компилируется
TypeScript'ом**, а корневой `tsconfig.json` это `strict: true` и `noImplicitAny: true`.

Значит тело без типов у параметров прекрасно работает в превью и **разваливает выгрузку**.
Пользователь узнаёт об этом не там, где ошибся, и не тогда, когда ошибся.

Лечить на этапе 4.1: либо редактор кода прогоняет тело через TS и показывает ошибку на
месте, либо экспорт проверяет заранее и отказывает внятно. Молчаливого расхождения между
тем, что видно, и тем, что выгружается, оставлять нельзя.

### Имя модуля не свободно

MAM резолвит `$a_b_c` в путь `a/b/c`, поэтому классы документа обязаны схлопываться на
папку, куда модуль положили. Иначе сборка ищет несуществующий пак и падает — то есть
«выглядит правильно, не собирается» ровно там, где проходит приёмка.

Путь вычисляется **из имён самих классов**, по их наибольшему общему префиксу:
`$bog_mysite_page` плюс `$bog_mysite_hero` дают `bog/mysite/` и файл `mysite.view.tree`;
один `$bog_mysite_page` даёт `bog/mysite/page/`. Оба случая резолвятся штатно, потому что
недостающий последний сегмент схлопывается на существующий префикс.

Обратное направление — переименовывать классы под выбранную папку — нарушило бы
«байт-в-байт из редактора», поэтому имена главнее пути, а не наоборот.

Если общий префикс короче двух сегментов, то есть классы из разных паков, экспорт
**отказывается** с внятным сообщением вместо выпуска несобираемого модуля.

### Порядок классов в файле обязателен

`class $A extends $['$B']` берёт базу в момент объявления, а генератор идёт по файлу
сверху вниз. Несортированный `.view.tree` даст `Class extends value undefined` — ровно то,
что сцена ловила на этапе 1. Топологическая сортировка живёт в `$bog_vmap_lang`: это
свойство объявлений `view.tree`, а не забота экспорта или сцены.

**Выгружается отдельный пак — свой репозиторий со своим деплоем.** `bog/` это реестр
паков, приложений он не содержит: каждое живёт отдельным репозиторием, зарегистрированным
в `bog.meta.tree` и клонируемым в `bog/<name>/`. Сам vmap устроен так же.

Критерий приёмки этапа экспорта: выгруженный пак подключается как пак и собирается
`npx mam` без единой правки руками.

## 10a. Как проверять

Разработка идёт на `-/test.html`, это штатная страница дев-сервера, и менять тут нечего.

**Но доступность классов в рантайме проверять только на `-/index.html`.** Замер на сцене:

| бандл | грузит | `class $mol_string` |
|---|---|---|
| `web.js` | `index.html` | **0** |
| `web.test.js` | `test.html` | 2 |

Бандл несёт лишь то, на что ссылается сам модуль, а тестовый дополнительно тащит половину
`mol`. Обычному $mol-коду это безразлично: ссылка в исходнике и есть то, что тащит модуль
в граф. У нас классы резолвятся **по имени в рантайме**, граф про них не знает, поэтому
документ с `$mol_string` живёт на `test.html` и падает на проде в
`this.$.$mol_string is not a constructor`.

Это не мелочь проверки, а следствие раздела 5: компоненты приезжают **донорским паком**,
и до этапа 2 сцена умеет ровно то, на что сослалась сама. Захардкоженный документ этапа 1
обязан жить в этих пределах, иначе проверка зелёная, а продукт мёртвый.

**Чего нельзя проверить автоматизированным браузером.** Вкладка под ним всегда `hidden`,
а Chrome в фоне замораживает рендер-цикл целиком, а не только `requestAnimationFrame`:
инлайновый `style.width` не сдвигает `getBoundingClientRect()`, страница не пересчитывает
даже раскладку. Значит недоступны для проверки все пути, привязанные к рендер-циклу, и в
первую очередь **доставка уведомлений `ResizeObserver`**. Механизм и его жизненный цикл
проверяются, живая доставка нет.

**Клавиши не доходят в запесоченный кадр, клики доходят.** Разностный замер: два кадра на
один URL сцены, единственная разница — атрибут `sandbox`. Незапесоченный ввод принимает,
запесоченный нет; тот же код, тот же жест, тот же инструмент. При этом `activeElement`
хоста после клика становится самим кадром, то есть указатель границу переходит и режим
«Запуск» работает. Chrome держит такой кадр отдельным процессом (OOPIF), куда
CDP-клавиатура не проходит.

Значит **ввод внутри документа проверяется только живым человеком** либо на сцене,
открытой верхним уровнем. Это навсегда, а не до конца сессии.

Отсюда правило: такие места помечать непроверенными явно, а не выдавать проверку механизма
за проверку поведения. Первым увидит их вживую тот, кто откроет стенд руками.

**Скриншот не доказывает композицию.** Кадр в автоматизированной вкладке создаётся по
запросу захвата, поэтому картинка выглядит живой даже при задушенном рендер-цикле, а путь
композиции может отличаться от живого. Прецедент на соседнем проекте: по такому наблюдению
объявили «событие `scroll` не приходит вообще» и переделали рабочий код, а причиной была
заморозка вкладки. Прежде чем объявлять поломкой то, что видно на скриншоте, померить сам
стенд: если `requestAnimationFrame` не тикает за 600 мс, выводы о событиях и о композиции
недействительны. Позиционирование, вёрстка и `getComputedStyle` при этом измеряются верно.

Вторая ловушка того же рода: `dispatchEvent` сконструированного `PointerEvent` **не заводит
активный указатель**, поэтому синтетический пинч даёт `NotFoundError` из
`releasePointerCapture` там, где живой ввод не даёт ничего. Ошибку в консоли при проверке
синтетикой сперва проверяй на происхождение по стеку, а уже потом обвиняй компонент.

## 11. Грабли, которые уже стоили времени

- Провод длиннее одного звена пишется через `=`. `<= Имя свойство` молча теряет второе
  звено и превращается в объявление свойства, см. раздел 1.
- В `attr *` ключ, который должен примениться до навигации (`sandbox`), ставить **до** `^`,
  см. раздел 4. Порядок ключей словаря это порядок `setAttribute`.
- Скомпилированные классы возвращать из `@$mol_mem` **завёрнутыми в объектный литерал**.
  Голый класс ячейка клеймит, и тег элемента превращается в кашу, см. раздел 3.
- Класс всегда именованный, имя и CSS подставлять через `JSON.stringify`, см. раздел 3.
- Декораторы в теле `new Function` не пишутся, применять вызовом после определения класса.
  Под `@$mol_mem` класть **каждое** свойство, иначе горячая правка его не увидит.
- **Сгенерированный код начинается со скобки.** Без `;` на предыдущей строке ASI склеит
  всё в `$( … )` и даст `TypeError: $ is not a function`.
- Поле атома называется **не** `имя()`. `$mol_wire_solo` копирует имя из базы, если та уже
  декорирована, а обёртке ставит имя с **хвостовым пробелом** (`solo.ts:14` и `:39`), так
  что свойство, декорированное и в сгенерированной базе, и в рукописном теле, лежит в
  `'bump ()'`. Искать через `Object.getOwnPropertyNames( inst )` с фильтром по суффиксу
  `()` и `trim()`, а не склейкой `name + '()'`. На S2 из-за этого молча не работал снапшот.
- Песочницу **не пересоздавать** между сборками, см. раздел 3.
- **В невидимой вкладке страница не раскладывается, и `getBoundingClientRect()` честно
  отдаёт 0×0.** Само не чинится: при возврате вкладки в графе `$mol_wire` ничего не
  меняется, и хост остаётся с нулями до следующей правки. Замер габаритов обязан иметь
  внешний триггер пере-замера.
- Стили узлов только через `$mol_style_attach`. `$mol_style_define` на чужой компонент
  перетирает его собственные стили.
- Кастомный атрибут на встроенном компоненте добавляется подклассом в `view.tree` с
  `attr * ^ my_attr <= …`, где `^` наследует родительские атрибуты.
- `$mol_view` рендерит не `div`, а тег по имени класса, и по умолчанию это `display: flex`.
- `$mol_textarea` это редактор кода, простое многострочное поле им не делается.
- `$mol_string` занял свойство `enter`, свой обработчик с таким именем сработает на каждом
  рендере.
- `setPointerCapture` перетаргечивает `click` и `dblclick`. Цель брать из `pointerdown`.
- `releasePointerCapture` бросает `NotFoundError` **не** когда захвата не было, а когда
  такого указателя нет среди активных. Для живого указателя это молчаливый no-op. Значит
  безусловный вызов в `$mol_touch.event_leave` безопасен, а `NotFoundError` в консоли при
  синтетических событиях — артефакт проверки: `dispatchEvent` сконструированного
  `PointerEvent` не заводит активный указатель.
- **`$mol_scroll` держит ровно ОДИН узел.** Он `display: grid` и ставит каждому прямому
  потомку `grid-area: 1/1`, так что двое детей рисуются друг поверх друга. Заголовок,
  положенный в скролл рядом со списком, ляжет на первые строки списка.
- **`minimal_height` в `view.tree` на высоту не влияет**, это число для виртуального окна
  `$mol_list`. Высоту даёт CSS, и пока её не задать, строки останутся по 40 px.
- **Метку загрузки вешать `::before`, а не `::after`.** `$mol_view` при подвисании
  оставляет детей прошлого удачного рендера, и на длинном списке всё поставленное в конец
  уезжает далеко за экран. Первым флекс-элементом метка видна и на холодном старте, и при
  смене источника.
- `$mol_plot_ruler_hor` и `_vert` обрезают линии по 1000 и 2000 px, для полноэкранного
  холста мало. Подкласс переопределяет `curve()` по `size_real()`.
- `stroke` это обычный `string` из `CSSStyleDeclaration`, а токен `$mol_theme.line` это
  `$mol_style_func`. Нужен явный `String( … )`, иначе TS2322.
- `[mol_view] { -webkit-appearance: none }` делает нативный чекбокс невидимым, оставляя
  его кликабельным. Лечится `appearance: auto` в стилях документа.
- **`[mol_view]` анимирует `transform` 0.2s** (`mol/view/view/view.css:5`). Камера на
  трансформе едет за указателем с задержкой, а `getBoundingClientRect()` во время перехода
  отдаёт промежуточную матрицу, из-за чего кажется, будто трансформ не применился вовсе.
  На узле, несущем камеру, ставить `transition: none`.
- **Замер габаритов нельзя вешать на таймер.** Он читает DOM, а таймер от правки исходника
  успевает выстрелить до коммита кадра: размеры уезжают от прошлой раскладки, а ошибка
  рендера ещё не на узле. Подписываться на отрисованное дерево через `dom_final()`.
- **`querySelector('[mol_view_error]')` не матчит сам узел**, а падает чаще всего именно
  корень документа. Проверять сперва себя, потом потомков. В атрибуте лежит только имя
  ошибки, сообщение $mol кладёт в текст узла.
- Фон страницы сцены задавать **инлайном** в её `index.html`. Правило из `mol/theme/theme.css`
  красит `body`, с хоста его не перебить (чужой origin), а инлайн держится с первого кадра,
  до загрузки `web.js`, иначе кадр моргает непрозрачным прямоугольником на старте.
- Класс из `view.tree` наследует `$`-базу, а не `$.$$`. Общую логику видов класть отдельным
  файлом в `namespace $`, без `view.tree`.
- Редекларация sub-компонента стирает биндинги, а ре-тайп keyed sub шадовит метод базы.
- `$mol_after_frame` не срабатывает в фоновой вкладке, он на `requestAnimationFrame`.
  Для сцены в iframe это актуально, брать `$mol_after_tick`.
- В `@$mol_action` подвисающие чтения ставить **первыми**, иначе первый клик проваливается.
- **Имя с `$` внутри строкового литерала тащит модуль в граф зависимостей.** Mam парсит
  и литералы тоже. На S1 строка `hint \$my_class $mol_view` в `.view.tree` уронила сборку
  с `Root package "my" not found`. Для нас это не мелочь: любое `$`-имя в дефолтных
  исходниках редактора и в примерах попадёт в граф. Демо-классы называть по пути
  собственного модуля (`$bog_vmap_spike_s1_demo`), тогда путь схлопывается на него же.
- `$mol_style_attach` не снимает старые style-элементы, см. раздел 3.
- Слэш со звездой внутри `//`-комментария выкидывает код из бандла при зелёном аудите.
- `git init` в паке **до** первой сборки. Дев-сервер намертво кеширует вывод «это не git»,
  лечится только рестартом.

**Вложенный кадр под пак (вариант D спайка S4) закрыт как не понадобившийся, а не как
проверенный.** Он дал бы документу собственный реактивный граф, то есть свойство сильнее

эту проверку заодно. Это рассуждение, не замер.

**Версионирование ленд-библиотек — вопрос ОСТРЕЕ, чем у паков, а не такой же.** У пака между

ленд-библиотеками начнут пользоваться вдвоём.

**Прежняя формулировка вопроса:** Документ ссылается на библиотеку, библиотека меняется,
документ ломается. Нужна ли фиксация версии и как она уживается с живым синком. Решать на
этапе 5, на модель документа не влияет.

## 13. Идиоматика $mol: что проверять на ревью

Раздел заведён 09.09.2026 после разбора со справочником по стилю. Проект большой, писали
его многие, и одинаковые вопросы задаются каждому. Здесь ответы, чтобы не задавать заново.

### Побочный эффект внутри `@$mol_mem` — брак, а не приём

Ячейка это **чистое вычисление**: читает другие ячейки, создаёт объекты, возвращает
значение. Писать в чужие ячейки, звать сеть, заводить таймеры и фибры она не смеет.
Побочные эффекты живут в `auto()` и в `@$mol_action`.

Симптом, по которому это ловится без чтения кода: ячейка, которой понадобилось отложить
собственный эффект — `Promise.resolve().then(…)`, `setTimeout`, поле-флажок мимо ячеек.
Отложение не лечит болезнь, а прячет её: эффект всё равно летит из вычисления, просто
позже. Правильный ответ один — вынести эффект в `auto()`, а ячейку оставить чистой.

**Чем это НЕ является.** Ячейка, которая проецирует состояние наружу и читается из
`auto()`, — приём законный и в паке несущий: так устроены шесть push-ячеек пейна
(`pack_push`, `doc_push`, `css_push`, `libs_push`, `spots_push`, `camera_push`). Значение
такой ячейки — это то, что уехало последним, и мемоизация здесь и нужна: без неё сообщение
летело бы на каждый перезапуск `auto()`, а не на изменение. Запрещено другое — **писать из
ячейки в чужие ячейки** (это петля инвалидации) и **заводить из неё фибры и таймеры**
(это жизненный цикл, которым ячейка не владеет). Отличать по вопросу: ячейка отражает
состояние наружу или порождает работу со своей судьбой.

**Почему залипает — точно.** Уведомление о протухании, пришедшее к ячейке, которая прямо
сейчас считается, отбрасывается на месте: `$mol_wire_pub_sub.absorb` первой строкой выходит
по неотрицательному курсору, а `stale` это −1. Значит залипает не «что-то рядом», а строго
та ячейка, чей ответ читают, если работа, которую она породила, успела записать результат
до конца её собственного вычисления. Отсюда и правило: ячейка не заводит фибр.

**Долг закрыт 09.09.2026:** `app/store/store.ts`, `boot()`. Он был `@$mol_mem`, стартовал
фибру заведения первого документа из микрозадачи и держал её в обычном поле мимо
реактивности. Теперь `boot()` — обычный метод и чистое чтение, а фибра лежит в бездепной
ячейке-держателе: у ячейки без зависимостей нет инвалидации, которую можно проглотить, а
повторное чтение отдаёт ту же фибру, поэтому второго документа не заводится.

У держателя фибры **нет `destructor`, и это осознанно**. Черновик переливается в документ
уже ПОСЛЕ того, как документ попал в список, то есть существует окно, в котором `boot`
отвечает `ready`, последний читатель отворачивается, а ячейку, которую никто не читает,
сметает вместе с тем, чем она владеет. Владей она фиброй — заливка оборвалась бы посреди
окна, и потерялся бы набранный пользователем текст, молча. Замерено, на это есть тест.
Ячейка держит рукоятку, а не жизнь: одноразовая фибра сама себя убирает по завершении.

### Своё вместо `view_rect()` — здесь осознанно

`$mol_view.view_rect()` существует и отдаёт коробку узла реактивно, но держится он на
`$mol_wire_watch`, а тот **перечитывает ячейку каждый кадр**; сам `mol` предупреждает
«Don't use if possible». Поэтому:

- **жесты** (`pane_rect()` в `app/pane/`) читают коробку сами: подписка на ежекадровое
  чтение внутри жеста дала бы перезапуск от той самой раскладки, которую жест и меняет,
  а первое чтение `view_rect()` вдобавок отдаёт `null` намеренно;
- **замер узлов документа** (`scene/measure.ts`) идёт своим `ResizeObserver`: узлов много,
  ежекадровый перечёт коробок у всех дороже наблюдателя, который будит только на изменение.

То есть это не «не знали про `view_rect`», а выбор между двумя механизмами `mol` по цене.

### Генерируемому коду документа декораторы дописываются выражениями

В строке, скармливаемой `new Function`, декоратор написать нельзя, поэтому
`$mol_mem( Класс.prototype, "свойство" )` идёт отдельным выражением после класса, как в
studio. Это не обход фреймворка, а единственная доступная форма; без неё свойство молча
не мемоизируется. Стили генерируемому классу — только `$mol_style_attach`, `$mol_style_define`
перетёр бы стили донорского класса.

### Остальное короткой строкой

- Всё, что можно выразить биндингом в `view.tree`, в `.view.ts` не пишется.
- Глобальные службы только через `this.$`, никаких прямых `window` и `document`.
- Стили только в `.view.css.ts`, `as any` запрещён; стилизуются отклонения от темы, а не
  то, что тема и так задаёт.
- Имена папок модулей без подчёркиваний: каждое `_` в имени класса это уровень папок.
