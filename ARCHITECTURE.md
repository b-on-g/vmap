# $bog_vmap — архитектура

Визуальный конструктор сайтов на бесконечном холсте. Живой $mol внутри, настоящий
исходник на выходе, Гипер База под спиной.

Документ читают **все** молеры перед работой над модулем. Решения здесь приняты,
спорить с ними в отдельной задаче можно, молча нарушать нельзя.

---

## 1. Главная ставка

**Документ vmap это один класс `view.tree`.**

Не «модель узлов, из которой можно сгенерировать код». Именно исходник, который
редактор парсит, правит через AST и сериализует обратно. Мышь и текстовый редактор
работают с одним и тем же байт-в-байт файлом.

Из этого следует три вещи разом:

- **экспорт исходников бесплатный**, потому что источник истины и есть результат экспорта;
- **обратная совместимость с mol-кодом бесплатная**, потому что чужой `.view.tree` можно
  просто открыть в редакторе;
- **реактивность бесплатная**, потому что связи между узлами это штатные `<=` и `<=>`,
  а считает их `$mol_wire`, а не наш код.

### Почему связь «любой узел с любым» не требует машинерии

В `view.tree` всякий именованный под-вид, на какой бы глубине он ни лежал, становится
**плоским свойством корневого класса**. Хак так и называется — `upper`
(`mol/view/tree2/class/props.ts:41`): он поднимает объявление из-под `<=` / `<=>` наверх,
в список свойств класса.

Живой пример: в `hyoo/map/map.view.tree:44` узел `Track_dot` объявлен на пятом уровне
вложенности (`Main → sub → Pane → graphs → Diag1 → graphs`), но при этом является
свойством `$hyoo_map`, а не `$mol_plot_group`.

Значит калькулятор, лежащий свободно на холсте, и метка, зарытая внутрь артборда, для
компилятора соседи. Провод между ними это одна строка:

```
	Calc $my_lib_calc                # деталь: объявлена, но не в sub → DOM не создаёт
	sub /
		<= Hero $mol_view sub /
			<= Price $mol_text title <= calc_result
	calc_result <= Calc result       # компилируется в this.Calc().result()
```

`<= Calc result` компилируется в `this.Calc().result()` (`mol/view/tree2/to/js/js.ts:44`,
функция `call_of` собирает цепочку вызовов). Ни сериализации, ни шины событий, ни
подписок. Потянул провод, редактор дописал строку, `$mol_wire` пересчитал.

## 2. Что берём из `$hyoo_studio`

[studio.hyoo.ru](https://studio.hyoo.ru/) это визуальный редактор одного $mol-компонента,
работающий в проде. Половина нашего фундамента там уже написана и обкатана. Забираем не
идеи, а код. Репозиторий `hyoo-ru/studio.hyoo.ru`, пак `studio` в `hyoo/hyoo.meta.tree:51`.

| Оттуда | Что закрывает |
|---|---|
| `component/component.ts` | модель узла: текст как истина, `tree()` как производная, `prop_tree()`, `prop_add`, `prop_drop` |
| `property/property.ts` | свойство и его сигнатура: `name`, `key` (`*`), `next` (`?`) через `$mol_view_tree2_prop_signature` |
| `library/library.ts` + `studio.view.ts` `library()` | палитра из любого задеплоенного пака |
| `studio.view.ts` `props_map()` | порты класса вместе с унаследованными, обходом цепочки |
| `studio.view.ts` `self_code()` | рантайм-сборка класса из трёх исходников |
| `studio.view.ts` `props_js()` / `props_css()` | нарезка JS и CSS по свойствам, гранулярность редактора кода |
| `value/bound/` | редактор биндинга, модельная сторона провода |

Три детали, до которых мы бы дошли только через грабли.

**Декораторы применяются вручную.** В строке JS, скармливаемой `new Function`, декоратор
написать нельзя. Studio дописывает `$mol_mem( $.$my_class.prototype, "prop" )` отдельными
выражениями после определения класса (`source_js_decorators()`). Без этого свойство просто
не мемоизируется, и это молчаливая поломка, а не ошибка.

**Стили только `$mol_style_attach`.** `self_code()` заканчивается вызовом
`$mol_style_attach( class_name, css )`. `$mol_style_define` тут применять нельзя, он бы
перетёр стили донорского класса.

**`predef` для `$mol_view`.** Собственные свойства `$mol_view` (`sub`, `attr`, `style`,
`event`, `field`, `dom_name`, `title`) в `web.view.tree` не попадают, потому что `$mol_view`
написан на TS. Studio дописывает их строкой-заглушкой перед парсингом (`library()`).
Копировать дословно, иначе палитра теряет базовые порты.

### Чего из studio НЕ берём

`self_code()` начинается со строки `$.$mol_wire_auto = parent.$mol_wire_auto`, то есть
превью делит планировщик реактивности с родителем и лезет в `parent`. Это требует
same-origin и убивает всякую изоляцию.

Нам это не нужно. Весь документ компилируется внутри сцены целиком, поэтому вся его
реактивность внутренняя, и общий планировщик не требуется. Инспекция wire-графа, ради
которой studio туда и лезет, у нас идёт через мост.

## 3. Рантайм-компиляция

Компилятор `view.tree` целиком браузерный, node-зависимостей в нём нет:

```
$mol_tree2_from_string( src )            →  AST
$mol_view_tree2_to_text( ast )           →  строка JS      (mol/view/tree2/to/text/text.ts:2)
new Function( '$', js )( sandbox )       →  живые классы
```

На выходе код вида `$['$my_page'] = class $my_page extends $['$mol_view'] {…}`, то есть
классы регистрируются в переданном объекте `$`. Передаём производный: `Object.create( $ )`
с добавленным `$.$ = $`. Инстанс создаём через `Class.make({ $: sandbox })`.

Компонент собирается из **трёх** исходников, как в studio: декларация `view.tree`, тело
класса на JS, стили. Порядок сборки в `self_code()`.

> `$mol_ambient` устарел, DI работает только через `this.$.X`. Классы, попавшие в
> производный `$`, разрешаются штатно, потому что цепочка прототипов ведёт к базовому.

**Классы обязаны возвращаться из `@$mol_mem`.** Объект, созданный внутри ячейки и не
возвращённый из неё, будет уничтожен при следующем пересчёте.

## 4. Граница безопасности

Пользовательский код исполняется **только внутри sandbox-iframe**, начиная с первого дня.
Ретрофитить границу позже означает переписать весь рендер, поэтому она закладывается сразу.

Берём `$mol_frame` и подкласс с добавленным атрибутом:

```
$bog_vmap_scene_frame $mol_frame
	attr *
		^
		sandbox \allow-scripts
```

`allow-scripts` **без** `allow-same-origin` даёт iframe уникальный opaque origin даже при
загрузке с собственного домена. Это работает на gh-pages, где отдельный origin взять негде.
Внутри нет доступа ни к `localStorage` хоста, ни к его IndexedDB, ни к `parent`, только
`postMessage`.

Совмещать `allow-scripts` с `allow-same-origin` для недоверенного контента **нельзя**:
такая пара снимает изоляцию полностью.

### Кто чем владеет

| | Хост (`$bog_vmap_app`) | Сцена (`$bog_vmap_scene`) |
|---|---|---|
| Текст документа | источник истины | производная копия |
| Парсер и AST | да | нет |
| Компиляция и исполнение | нет | да |
| Камера и геометрия | источник истины | получает как данные |
| Выделение, ручки, провода | да, на своём оверлее | нет |
| Гипер База, ключи, сеть | да | **нет доступа вообще** |
| Палитра, инспектор, редактор кода | да | нет |

Поток односторонний: хост правит текст, шлёт в сцену, сцена перекомпилирует. Назад идут
только измеренные размеры узлов, значения портов для инспектора и ошибки компиляции.

Ключевое следствие: чужой код не видит ключей пользователя, потому что сеть живёт в хосте.

### Режимы через `pointer-events`

Оверлей хоста лежит прозрачным слоем поверх iframe.

- **Правка**: `pointer-events: auto` на оверлее. Все указательные события ловит хост,
  до сцены они не доходят. Ретрансляция не нужна.
- **Запуск**: `pointer-events: none`. События проваливаются в iframe, живой компонент
  работает по-настоящему.

Переключение режима это одна строка стиля, а не второй рендер.

## 5. Библиотеки компонентов

Пользователь должен собирать свои компоненты и переиспользовать их в других приложениях.
Механика для этого уже существует, придумывать нечего.

**Библиотека компонентов это задеплоенный MAM-модуль.** Сборка кладёт рядом с `web.js`
файл `web.view.tree` (`mol/build/build.node.ts:576`) — полное дерево классов бандла с их
базами и свойствами. Studio этим и живёт: тянет `<pack>/-/web.view.tree` для списка
классов, грузит `<pack>/-/web.js` для их поведения.

Отсюда два источника, оба сводятся к одному united-дереву:

1. **Донорский пак.** Любой URL задеплоенного $mol-приложения. По умолчанию
   `https://mol.hyoo.ru`, то есть вся стандартная библиотека сразу в палитре. Любое
   $mol-приложение в мире становится источником компонентов без нашего участия.
2. **Ленд-библиотека.** Компоненты живут в Гипер Базе исходниками (три файла на компонент).
   Публикация и подключение идут ссылкой, деплой не нужен, шарится как всё остальное в базе.

Сцена обрабатывает оба одинаково. Донорский пак приезжает готовым `web.js`,
ленд-библиотека приезжает исходниками и компилируется той же цепочкой, что и сам документ.

Порты любого класса, включая унаследованные, даёт обход цепочки наследования по
united-дереву (`props_map` в studio).

**Круг замыкается на экспорте.** Выгруженный документ это MAM-модуль, а MAM-модуль после
деплоя это донорский пак. То есть любой собранный в vmap сайт автоматически становится
библиотекой компонентов для следующего.

## 6. Файлы

Требование: загружать файлы в пространство, делиться ими, использовать в приложениях.

**Ассет это отдельный blob-ленд Гипер Базы**: байты плюс имя и MIME-тип. Именно отдельный
ленд, а не поле документа, потому что тогда файлом можно поделиться самостоятельной ссылкой
и переиспользовать в разных документах. Документ держит `atom_link_to` на ленд, то есть
ссылку, а не копию.

Правила из практики, нарушение которых стоит суток отладки:

- запись blob и заведение нового ленда **только из фибры**, иначе вечный PoW-ретрай;
- авто-синк blob-лендов делается override `remote()` **в схеме**, не во вьюхе;
- `atom_link_to` требует `.remote(store)` после `.ensure(null)`, иначе file pawn не пушится.

### Схема `asset:` и кто её подменяет

В документе ассет адресуется устойчивым идентификатором: `uri \asset:7f3a…`. Подменяет
его тот, кто рендерит.

- **Сцена** подменяет на `blob:` непосредственно перед компиляцией, текстовой заменой.
- **Экспорт** подменяет на относительный путь `./assets/<name>` и кладёт файл в модуль.

Документ при этом хранит один и тот же id, и ни сцена, ни экспорт не пишут обратно.

Байты доезжают до сцены **по мосту**, а не по URL. `blob:`-ссылка, созданная хостом,
привязана к его origin и в opaque-origin песочнице не откроется. `postMessage` передаёт
`ArrayBuffer` через structured clone, в том числе transferable, сцена сама зовёт
`URL.createObjectURL`. Доставка ленивая: сцена просит ассет по id, когда он реально
понадобился.

## 7. Раскладка модулей

Корень `bog/vmap/` держит **только** `vmap.meta.tree` и документацию, без кода. Причина
в том, что `$bog_vmap_scene` тащит родительскую папку `bog/vmap/` в граф зависимостей, и
если положить редактор в корень, он уедет в бандл сцены. Приложения живут в подпапках,
как у `bog/smalljs/app/` и `raggu/web/app/`.

```
bog/vmap/
├── vmap.meta.tree
├── ARCHITECTURE.md   PLAN.md
│
├── lang/       $bog_vmap_lang     AST: узел, свойство, биндинг. Порт studio, ничего не исполняет
├── lib/        $bog_vmap_lib      библиотеки: донорский пак и ленд-библиотека, united-дерево, порты
├── asset/      $bog_vmap_asset    файлы: blob-ленды, схема asset:, доставка, шаринг
├── bridge/     $bog_vmap_bridge   протокол postMessage, общий для обеих сторон
│
├── app/        $bog_vmap_app      ПРИЛОЖЕНИЕ-РЕДАКТОР (index.html)
│   ├── pane/                      камера, оверлей, culling
│   ├── frame/                     артборд
│   ├── card/                      свободная деталь на холсте
│   ├── wire/                      провода поверх сцены
│   ├── code/                      редактор кода узла
│   ├── palette/                   палитра
│   ├── inspect/                   инспектор свойств
│   ├── doc/                       схема Гипер Базы и операции над документом
│   └── export/                    выгрузка MAM-модуля
│
└── scene/      $bog_vmap_scene    ПРИЛОЖЕНИЕ-ПЕСОЧНИЦА (index.html)
```

Реестра классов в сцене больше нет. Компоненты приезжают донорским паком по URL, поэтому
в бандл сцены их зашивать не требуется.

## 8. Холст

### Камера

`$mol_touch` берём как есть, плагином на оверлее. Он уже отдаёт `pan` (вектор) и `zoom`
(скаляр) из pointer-событий, включая пинч, и уже переводит экранные координаты в мировые
в `action_point()` (`mol/touch/touch.view.ts:62`). Хит-тестинг почти готов.

Зум изотропный, одним скаляром, как в Фигме. Двухосный `scale` из `$mol_plot_pane` не нужен.

### Почему не `$mol_plot_pane`

Узлы обязаны быть настоящими компонентами с инпутами, фокусом и скроллом, а pane это
`$mol_svg_root`, заточенный под графики: авто-фит по `dimensions()` данных, раскраска по
hue, свой culling графиков (`mol/plot/pane/pane.view.ts:141`).

Сцена это **HTML-слой** под `transform: translate() scale()`, узлы позиционируются абсолютно
в мировых координатах. Из плота берём `$mol_touch` и линейки `$mol_plot_ruler` для фоновой
сетки, сам pane не берём. Идею culling копируем: `dimensions_viewport()` в
`pane.view.ts:180` даёт готовую формулу перевода вьюпорта в мировые координаты.

### Артборды и свободные детали

**Артборд** это узел документа, играющий корень страницы. Внутри артборда редактор
работает не по координатам, а **по дереву**: перетаскивание вставляет узел в `sub` родителя
на позицию, обратная связь это линия вставки между детьми. Вёрстка остаётся родным
$mol-флексом, поэтому экспорт даёт нормальный адаптивный код без `position: absolute`.

**Свободная деталь** лежит на холсте по координатам `x, y` вне артбордов. Её класс тоже
компилируется, но в `sub` артборда она не входит, а значит DOM не создаёт. Существует она
ради своих портов.

Обе сущности это свойства одного корневого класса документа, см. раздел 1.

## 9. Документ в Гипер Базе

Схема остаётся **чистой**. `static @$mol_action` на сущности ломает синхронизацию, весь
CRUD живёт во вьюхах.

Текст храним **по узлам**, отдельным `atom_str` на узел, а не одним `sand_ordered` на весь
документ. Причины две: `sand_ordered` теряет текст при одновременной правке и квадратичен
на запись (76 мс на правку при 500 правках). Совместное редактирование получается
по-узловое, LWW. Настоящий co-editing внутри одного узла откладываем до починки движка.

Числа держим в `atom_real`. `atom_bint` не переживает круг записи и чтения: пишешь `3000n`,
читаешь `null`.

Мастеров модуль не прописывает и `masters()` не перебивает. Узел выбирает приложение.

## 10. Экспорт

Выгружается настоящий MAM-модуль, а не абстрактный «проект»:

```
<name>/
├── <name>.view.tree      документ как есть, байт-в-байт из редактора
├── <name>.view.ts        JS-логика узлов, собранная в namespace $.$$
├── <name>.view.css.ts    стили
├── <name>.meta.tree
├── assets/               файлы, ссылки asset: переписаны на относительные пути
└── index.html
```

Критерий приёмки этапа экспорта: выгруженный модуль кладётся в `bog/` и собирается
`npx mam` без единой правки руками.

## 11. Грабли, которые уже стоили времени

- Скомпилированные классы **возвращать** из `@$mol_mem`, иначе ячейка их уничтожит.
- Декораторы в теле `new Function` не пишутся, применять вызовом после определения класса.
- Стили узлов только через `$mol_style_attach`. `$mol_style_define` на чужой компонент
  перетирает его собственные стили.
- Кастомный атрибут на встроенном компоненте добавляется подклассом в `view.tree` с
  `attr * ^ my_attr <= …`, где `^` наследует родительские атрибуты.
- `$mol_view` рендерит не `div`, а тег по имени класса, и по умолчанию это `display: flex`.
- `$mol_textarea` это редактор кода, простое многострочное поле им не делается.
- `$mol_string` занял свойство `enter`, свой обработчик с таким именем сработает на каждом
  рендере.
- `setPointerCapture` перетаргечивает `click` и `dblclick`. Цель брать из `pointerdown`.
- Класс из `view.tree` наследует `$`-базу, а не `$.$$`. Общую логику видов класть отдельным
  файлом в `namespace $`, без `view.tree`.
- Редекларация sub-компонента стирает биндинги, а ре-тайп keyed sub шадовит метод базы.
- `$mol_after_frame` не срабатывает в фоновой вкладке, он на `requestAnimationFrame`.
  Для сцены в iframe это актуально, брать `$mol_after_tick`.
- В `@$mol_action` подвисающие чтения ставить **первыми**, иначе первый клик проваливается.
- Слэш со звездой внутри `//`-комментария выкидывает код из бандла при зелёном аудите.
- `git init` в паке **до** первой сборки. Дев-сервер намертво кеширует вывод «это не git»,
  лечится только рестартом.

## 12. Открытые вопросы

**Пересборка класса убивает состояние живого экземпляра.** Правишь код узла, класс
компилируется заново, инстанс приходится создавать заново, введённый в него текст пропадает.
Варианты: подмена прототипа с сохранением ячеек `@$mol_mem`, либо снапшот и восстановление
состояния по именам свойств, либо принять потерю на время редактирования. Решается спайком S2.

**Версионирование ленд-библиотек.** Документ ссылается на библиотеку, библиотека меняется,
документ ломается. Нужна ли фиксация версии и как она уживается с живым синком. Решать на
этапе 5, на модель документа не влияет.

**Несколько страниц в одном документе.** Каждая страница отдельный артборд, экспорт собирает
приложение с роутером. Отложено до этапа 6.

Вопрос про порты встроенных компонентов **закрыт**: их даёт `web.view.tree` донорского пака,
см. раздел 5.
