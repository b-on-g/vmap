# $bog_vmap — план работ

Архитектурные решения в [ARCHITECTURE.md](./ARCHITECTURE.md). Здесь только порядок и
приёмка. Каждая задача нарезана под одного молера.

Статус: `[ ]` не начата, `[~]` в работе, `[x]` принята.

Донор кода на весь проект: `hyoo-ru/studio.hyoo.ru` (пак `studio` в `hyoo/hyoo.meta.tree:51`).
Что именно оттуда берём, перечислено в разделе 2 архитектуры. Перед задачами этапов 2 и 4
клонировать репозиторий и прочитать соответствующий файл.

## Этап 0. Спайки

Три независимые проверки. Все три ставят под сомнение фундамент, поэтому идут **до**
каркаса и запускаются параллельно тремя молерами. Живут в `bog/vmap/spike/`, после
принятия решения выбрасываются целиком.

- [ ] **S1. Рантайм-сборка компонента из трёх исходников.** Референсная реализация уже есть:
  `self_code()` в `studio/studio.view.ts`. Повторить её на голой странице: `view.tree`, тело
  класса на JS и CSS собираются в одну строку, скармливаются `new Function`, класс
  инстанцируется и рендерится.
  **Приёмка:** правишь любой из трёх исходников, компонент перерисовывается; биндинг
  `<= Other prop` между двумя под-видами работает реактивно; свойство с `@$mol_mem`,
  применённым через `source_js_decorators()`, действительно мемоизируется.

- [ ] **S2. Горячая подмена.** Что происходит с живым экземпляром при перекомпиляции класса
  и можно ли сохранить состояние. Проверить три варианта из раздела 12 архитектуры.
  **Приёмка:** вывод в `spike/S2.md` с рекомендацией и замером, плюс рабочий прототип
  выбранного варианта.

- [ ] **S3. Изоляция.** `$mol_frame` с подклассом, добавляющим `sandbox="allow-scripts"`.
  Хост шлёт текст документа и `ArrayBuffer` файла через `postMessage`, сцена компилирует,
  рендерит, делает `createObjectURL` и отдаёт назад измеренные размеры.
  **Приёмка:** из сцены недоступны `parent`, `localStorage` и IndexedDB хоста, при этом
  рендер, доставка байтов и обратный канал работают. Отдельно проверить, что
  `parent.$mol_wire_auto` действительно недоступен, то есть трюк studio исключён осознанно,
  а не по недосмотру.

Дальше идти, пока S1 и S3 не приняты, **нельзя**: на них стоит всё остальное.

## Этап 1. Каркас

- [ ] **1.1. Завести пак.** `git init` в `bog/vmap` **до** первой сборки, `pack vmap` в
  `bog/bog.meta.tree`, репозиторий `b-on-g/vmap`, лицензия MIT. Скелет по раскладке из
  раздела 7 архитектуры, корень без кода.
- [ ] **1.2. `$bog_vmap_bridge`.** Типизированный протокол `postMessage` на обе стороны:
  `doc_set`, `camera_set`, `mode_set`, `asset_put` в сцену; `sizes`, `port_values`,
  `asset_want`, `error` обратно.
- [ ] **1.3. `$bog_vmap_scene`.** Приложение-песочница. Принимает текст, компилирует по S1,
  рендерит, отвечает по мосту.
- [ ] **1.4. `$bog_vmap_app` + `pane`.** Оболочка редактора, камера на `$mol_touch`,
  кадр сцены, прозрачный оверлей, переключение `pointer-events` между правкой и запуском.
  Фоновая сетка на `$mol_plot_ruler`.

**Приёмка этапа:** пустой холст панится и зумится, захардкоженный документ рендерится
внутри песочницы, кнопка «Запуск» делает компонент кликабельным.

## Этап 2. Документ и узлы

- [ ] **2.1. `$bog_vmap_lang`.** Портировать `component/component.ts` и
  `property/property.ts` из studio. Не переписывать своё, взять работающее и покрыть
  тестами на round-trip: текст → AST → правка → текст, диффом должна отличаться ровно
  одна строка.
- [ ] **2.2. `$bog_vmap_lib` — донорский пак.** По `library()` из studio: тянуть
  `<pack>/-/web.view.tree`, парсить, нормализовать, приклеивать `predef` для `$mol_view`.
  Плюс `props_map()` для портов с наследованием и `united()` для склейки библиотеки с
  документом. Дефолтный пак `https://mol.hyoo.ru`.
- [ ] **2.3. `doc` — схема Гипер Базы.** Чистая схема без `static @$mol_action`, текст по
  узлам в `atom_str`, координаты в `atom_real`, CRUD во вьюхах.
- [ ] **2.4. `palette` + добавление узла.** Список классов берётся из `lib`, а не из
  захардкоженного перечня. Перетаскивание на холст дописывает объявление в AST.
- [ ] **2.5. `card` — выделение, перетаскивание, ресайз.** Ручки на оверлее хоста. Цель
  клика брать из `pointerdown`, потому что `setPointerCapture` перетаргечивает `click`.
- [ ] **2.6. `inspect`.** Инспектор свойств выделенного узла, правка пишет в AST. Типовые
  редакторы значений подсмотреть в `studio/value/`.
- [ ] **2.7. Culling.** Узлы вне вьюпорта не рендерятся. Замер на 1000 узлов.

**Приёмка этапа:** документ из десятка узлов собирается мышью, переживает перезагрузку
страницы и подтягивается на втором устройстве.

## Этап 3. Связи

Ради этого этапа всё и затевалось.

- [ ] **3.1. `wire`.** SVG-слой поверх сцены, кривые Безье, тяга от порта к порту,
  подсветка совместимых целей по типу. Порты уже есть из 2.2.
- [ ] **3.2. Запись биндинга.** Соединение дописывает в AST строку вида
  `title <= Calc result` или заводит промежуточное свойство, когда цель занята. Модельную
  сторону взять из `studio/value/bound/`.
- [ ] **3.3. Значения на проводах.** Сцена шлёт текущие значения портов по мосту, хост
  подписывает провод. Троттлинг обязателен.
- [ ] **3.4. Демо-калькулятор.** Свободная деталь с портом `result`. Сценарий из
  постановки: считаешь на калькуляторе, тянешь провод в метку внутри артборда, число
  появляется на странице.

**Приёмка этапа:** демо-сценарий проходится мышью, без единой строки, написанной руками.

## Этап 4. Редактор кода

- [ ] **4.1. Три таба на узел.** `$mol_textarea` для `view.tree`, JS и CSS, как в
  `Source_type` у studio. Правка текста перестраивает AST, правка мышью обновляет текст.
  Ошибки парсера подсвечиваются, документ при этом не разваливается.
- [ ] **4.2. Нарезка по свойствам.** Режим «редактирую одно свойство» поверх `props_js()`
  и `props_css()` из studio. Именно эта гранулярность делает связывание переменных между
  компонентами практичным.
- [ ] **4.3. Сохранение состояния при перекомпиляции.** Реализация варианта из S2.
- [ ] **4.4. Ошибки.** Ошибка компиляции и рантайм-исключение из сцены доезжают до хоста и
  показываются на узле, а не только в консоли.

**Приёмка этапа:** узел, целиком написанный в редакторе кода, работает наравне с узлом
из палитры и связывается с ним проводом.

## Правила работы молеров

1. Перед задачей прочитать [ARCHITECTURE.md](./ARCHITECTURE.md) и нужный reference из
   `bog/mol_skill/references/`.
2. Если задача помечена как порт из studio, **сначала прочитать оригинал**, потом писать.
   Переписывание своими словами того, что уже работает в проде, считается браком.
3. Билд руками не запускать. Дев-сервер собирает в фоне, результат смотреть в
   `bog/vmap/app/-/web.audit.js`, сверяя свежесть по `web.js`, а не по mtime аудита.
4. Стили только в `.view.css.ts`, `as any` запрещён.
5. Не трогать чужой этап. Пересечения по файлам выносить в отдельную задачу.
6. `$mol_style_define` на компонент, объявленный не в своём модуле, не писать.
