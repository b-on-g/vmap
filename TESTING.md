# Как гонять тесты в паке, где работают несколько молеров

Два правила и один инструмент. Оба правила выведены дорого, инструмент к ним прилагается.

---

## 1. Красный тест в ЧУЖОМ модуле — сперва пересобрать его начисто

Бандл соседа отстаёт от его исходника: дев-сервер собирает по запросу, и пока никто не
дёрнул `-/node.test.js` того модуля, там лежит вчерашний код. Падение показывает
вчерашнюю ошибку, которую автор, возможно, уже починил час назад.

Случай из практики, 04.09.2026: `$bog_vmap_lib` отдавал красный тест
`every port names the class it came from`, диагноз по выводу был верен по существу
(`props_owner` обходил цепочку наследования в обратную сторону против `props_map`), но
к тому моменту автор уже нашёл это своим же тестом и починил. Красным был бандл, не код.

**Когда молеров несколько, красный тест перестаёт быть сигналом сам по себе.** Сигналом
становится **красный тест, который держится дольше одной пересборки**. Замерено 09.09.2026:
за одну волну четверо ловили чужую красноту пять раз, каждый раз это был сосед в середине
правки, и каждый раз через минуту становилось зелено — причём имя красного теста успевало
смениться между прогонами, так что «тот же самый» тоже проверять бесполезно.

**Порядок действий перед тем, как сообщать о чужой поломке:**

```
rm -rf bog/vmap/<чужой модуль>/-
curl -s -o /dev/null --max-time 300 --retry 4 --retry-delay 8 --retry-all-errors \
	http://localhost:9080/bog/vmap/<чужой модуль>/-/node.test.js
node bog/vmap/<чужой модуль>/-/node.test.js
```

Первый запрос после `rm` может отдать 404 или HTML-ошибку из-за гонки со сборкой.
Это не поломка, перезапросить.

---

Там же про **счётчик тестов**: `lang` и `lib` тянут к себе четыре модуля, поэтому число
тестов в чужом бандле растёт от чужого коммита. «Стало больше» само по себе не говорит,
кто их написал, и объяснять дельту своими правками — типовая ошибка в свою пользу. Сверять
по истории конкретного файла (`git log -- <путь>`), а не по разнице чисел.

## 1a. Отладочную пробу НЕ клади внутрь `$mol_test`

Замер печатается броском: `$mol_assert_equal` в сообщении значений не показывает, поэтому
соблазн написать `throw new Error( 'probe ' + … )` прямо в тесте велик. Так делать нельзя,
и цена платится не автором.

Рабочее дерево общее, а сборка берёт именно его, а не коммиты. Проба внутри `$mol_test` —
это красный тест у всех, кто тянет твой модуль. Дальше работает ловушка из пункта 4: первый
красный кладёт прогон, `node.audit.js` после него не создаётся вовсе, а `web.audit.js`
успевает записаться зелёным. У соседа остаётся один зелёный аудит при непрошедшей сборке и
чужая поломка в его собственном модуле, которую он час будет искать у себя.

Замерено 09.09.2026: две пробы подряд в `lang/lang.test.ts` остановили сборку `swap` и
`code`, и первую из них едва не записали в поломку соседнего модуля.

**Как надо.** Проба — обычная функция или отдельный скрипт поверх СОБРАННОГО бандла, как
трассировщик ниже: бандл делает `module.exports = $`, так что снаружи доступно всё, что
нужно замерить. Дерево при этом остаётся собираемым в любой момент, а печатать можно
сколько угодно.

## 2. Тишина в прогоне не значит успех

`$mol_test_run()` реджектится на ПЕРВОМ падении, `$mol_test_complete()` после этого не
зовётся, а реджект глотает `mol/report/handler`. В stdout при этом не будет ни строчки, и
процесс останется жить на file-watcher'ах. То есть **упавший ассерт выглядит ровно так же,
как зависший тест**: тишина и не завершающийся процесс.

Отсюда два следствия. Гонять прогон под таймаутом, а не ждать. И прежде чем искать
бесконечный цикл — проверить, не упал ли просто ассерт.

## 3. Имя с долларом в строке или комментарии — мина

Граф зависимостей MAM ищет `$имя` не только в коде, но и в **строковых литералах** и в
`/** */`-комментариях, и пытается разрешить его в пакет. Несуществующее имя валит сборку
всего модуля с `Root package "<имя>" not found`, причём страдает не только автор: имя
модуля тянет за собой родительскую папку, поэтому одна строка в тесте останавливает
работу всем.

За одну волну капкан сработал дважды: `$class` в докблоке `app/publish/publish.ts` уронил
сборку всего `app/`, `'$doc'` ключом фикстуры в `scene/measure.test.ts` уронил `scene` и
задержал деплой.

Четвёртый случай 09.09 бил не по фикстуре, а по продуктовому значению: дефолт имени
корня `my_site_page` с долларом в литерале `view.tree` дал `Root package "my" not found`,
потому что пака `my` не существует; и второй раз — на слове `$name` в докблоке, которым
объясняли первое. Доллар к такому имени приклеивается выражением, в текстах пишется без него.

**Правило:** в фикстурах, комментариях И продуктовых литералах доллар ставить только перед
именем реально существующего класса. Нужен искусственный ключ — писать его без доллара (`root`, `doc`)
или собирать из переменной. Проверять свой дифф перед коммитом:

```
git diff --cached -U0 | grep -nE '^\+.*\$[a-z_]+' 
```

## 4. Зелёный аудит после упавшей сборки — вчерашний аудит

Если сборка упала до стадии аудита (например на графе зависимостей), файлы
`-/web.audit.js` и `-/node.audit.js` остаются от прошлого удачного прогона и продолжают
говорить «Audit passed». Проверять по ним нечего: они описывают код, которого уже нет.

Замерено 08.09.2026: под этим прикрытием в `scene/measure.ts` жила ошибка типа, которую
node-аудит поймал сразу, как только сборка дошла до аудита.

Третья грань, замерена там же: сборка гоняет тесты в пайплайне, и первый красный тест
кладёт прогон со статусом 1. После этого `node.audit.js` не создаётся вовсе, а
`web.audit.js` успевает записаться зелёным. В каталоге остаётся один зелёный аудит и ни
одного красного при не прошедшей сборке. И тесты на протухшем бандле проходят зелёными,
показывая вчерашний код.

Четвёртая грань, 09.09: **чужой воркспейс MAM внутри модуля** (стрельнувший не в том
каталоге `npx mam` или клон — свой `.git`, `mam.ts`, `mol/`) делает `web.audit.js` всего
`app` постоянно красным (`TS2451 Cannot redeclare '_$_'`, `TS2649 Cannot augment module
'$'`), при зелёном node-аудите и зелёных тестах. Неотслеживаемое в коммиты не уезжает,
но одна из трёх проверок обесценивается для всех. Признак: в тексте ошибки нет ни одного
твоего файла, а есть `mam.ts`. Лечится удалением каталога его владельцем.

**Правило:** отличать тремя проверками разом — **код выхода сборки**, **наличие обоих**
файлов аудита, **их время** относительно исходников. `exit:0` и отсутствие
`fail / Root package … not found` в хвосте лога — часть приёмки, а не деталь.

### 4а. В негативном прогоне протухший бандл врёт КРАСНЫМ

Четвёртая грань той же ловушки, и она злее трёх предыдущих, потому что подтверждает то,
что ты и хотел увидеть. Замерено 09.09.2026.

Ломать продуктовое поведение принято выражением-заглушкой, и `if( false )` — первое, что
приходит в руку. Но мёртвую ветку TypeScript сужает, тип возврата метода после этого
меняется, и сборка падает **на аудите**, до стадии бандла. `node.test.js` при этом
остаётся от ПРЕДЫДУЩЕЙ поломки, трассировщик честно гоняет его и печатает падение
прошлого негативного прогона. Выглядит это как удача: сломал — покраснело.

Замер: седьмую поломку подряд подтвердил тест, который на самом деле относился к шестой.
Заметно стало только по времени файлов — исходник оказался новее бандла.

**Как надо.** Ломать так, чтобы код остался типово корректным: не `if( false )`, а условие,
которое ложно по данным (`includes( 'ключ, которого нет' )`). И **не запускать тесты, пока
бандл старше исходников** — одна строка перед прогоном, которая честнее любого код-ревью:

```
[ -n "$(find bog/vmap -path '*/-*' -prune -o -name '*.ts' \
	-newer bog/vmap/<модуль>/-/node.test.js -print | head -1)" ] \
	&& echo 'ПРОТУХШИЙ БАНДЛ, тесты не гонялись' && exit 1
```

`-prune` на папки сборки обязателен, иначе проверка врёт в обратную сторону: mam кладёт
в `-/` и `-node/` свои `.d.ts`, и они по определению новее бандла. Замерено там же —
первая версия проверки объявила протухшим свежий зелёный прогон.

## 5. Перезапуск фибры не перечитывает мир

Факт уровня пака, замерен 09.09.2026 инструментированным прогоном в `app/store/`.

Фибра, подвесившаяся на промисе, после его разрешения запускает свою задачу С НАЧАЛА. Но
начало это видит не сегодняшний мир, а свой собственный: чтение ячейки изнутри фибры идёт
через одноразовую задачу, которая кэшируется в самой фибре по позиции, и на перезапуске
задача в той же позиции переиспользуется вместе с записанным значением. То есть **все
чтения проигрываются из кэша фибры**, а не выполняются заново.

Замер: `doc_first` подвесили посреди заливки черновика уже после того, как документ попал
в список. На втором заходе список внутри фибры прочитался ПУСТЫМ, хотя снаружи в нём была
одна ссылка.

Из этого следуют две вещи сразу.

- **Проверка в начале фибры охраняет от чужого, а не от своего.** «Если объект уже есть,
  выйти» — это защита от документа, приехавшего с другого устройства ДО старта фибры.
  Свой собственный, наполовину заведённый, такая проверка не увидит и не бросит.
- **Поэтому долгая запись доходит до конца.** Перезапуск посреди заливки не отскакивает по
  ранней проверке, а доливает начатое. Ломается это ровно тогда, когда кто-нибудь решит
  «сделать проверку честнее» и заставит её перечитывать состояние напрямую.

**Для тестов:** тест, который подвешивает фибру и ждёт, что после пробуждения она увидит
свежее состояние, проверяет несуществующее поведение. Состояние надо проверять снаружи
фибры, а изнутри — считать, что мир застыл на моменте её старта.

## 6. Зелёный у автора, красный у соседа — это не бандл, это тест

Два дефекта теста, которые выглядят ровно как протухший бандл соседа (замерено 09.09.2026,
`app/inspect`, `shelf`):

- **Живые вью сравнивать только по тождеству.** `$mol_assert_like( one.sub(), [ one.Empty() ] )`
  уходит глубоким подобием внутрь машинерии вью, и результат зависит от того, что успело
  посчитаться: у автора проходит, у соседа с другим порядком прогона падает.
  `$mol_assert_equal` по ссылке точнее и не зависит от порядка.
- **Запись через замыкание стенда не роняет ячейку.** Если панель в тесте получает
  источник обычным замыканием, `one.source( … )` меняет переменную, но `Node().tree()`
  держит закэшированный провалившийся разбор, и тест требует от панели того, чего в этой
  обвязке быть не может. Второе состояние — второй экземпляр, а не запись в первый.

Прежде чем сказать соседу «пересобери», прогнать свой тест в чужом порядке: красный,
который приходит только ко второму прогонщику, чаще всего его и слушается.

**Пустой `web.css` не значит, что сырой `.view.css` не подхватился.** Собранный `-/web.css`
это 38 байт «CSS compiles into js bundle now!»: mam укладывает сырые `.view.css` в `web.js`,
и искать своё правило надо поиском по `web.js`, дословно, вместе с комментарием. Замерено
09.09 (`shelf`, `app/code/code.view.css`).

**Скрытая вкладка Chrome ломает адрес и перерисовку по построению, а не по случайности.**
`$mol_state_arg.href` пишет `location` внутри `$mol_after_frame`, и `watch` атома
переназначает себя тем же кадром (`mol/state/arg/arg.web.ts`, `mol/wire/atom/atom.ts`);
`requestAnimationFrame` в скрытой вкладке не тикает. Значит после клика документ может
быть создан, а список не вырастет и адрес не сменится — консоль чистая, работа не доезжает
до экрана. «Второй клик сработал» это кадр, который иногда приходит. Замерено 09.09
(`shelf`, по исходникам mol; `eyes`, прод): всё, что читается через DOM, адрес или список,
в скрытой вкладке не считается; мерить через API хоста и писать «DOM не проверен».

**Негативный прогон ловит и тест, а не только код.** Дважды за волну 09.09 (`fix`) первая
версия теста проходила и на старом правиле, то есть не доказывала ничего, и это показал
только негативный прогон: вернул старое правило — тест остался зелёным. Тест, который не
краснеет от отката правки, переписывать до того, как отчитываться.

## 4б. Негативный прогон врёт и с другой стороны: `catch` ловит не поломку, а ожидание

Пара к 4а. Там врал протухший бандл, здесь — сам способ ловить. Если проверка «сломал —
покраснело» обёрнута в `try/catch` ВНЕ фибры, подвисшее чтение (ячейка ждёт данных и
бросает промис) попадёт в `catch` и будет засчитано как пойманное падение. Прогон подтвердит
поломку там, где просто ждали данных.

Вторая грань того же: проверка, которая ломает пустоту, не краснеет никогда — например,
переименование корня в его же имя после смены дефолта. Видно только если печатать и
«НЕ пойман» тоже, а не считать молчание успехом.

**Правило:** проверки негативного прогона гонять внутри фибры (`$mol_wire_sync`/задача),
чтобы промис ожидания не маскировался под исключение; каждую поломку печатать в обе
стороны — «пойман» и «НЕ пойман»; поломка, которая не покраснела, это дыра в покрытии или
в самой поломке, и её надо разобрать, а не пропустить. Замерено 09.09.2026 на W15.

## Трассировщик: все тесты и все падения вместо первого

Бандл делает `module.exports = $`, поэтому его можно взять снаружи, забрать список тестов
себе и прогнать самому. Разница с обычным запуском в трёх вещах: печатает ВСЕ падения, а
не первое; называет виновника по имени; не выходит из процесса через секунду.

Своему планировщику оставляем пустой список и глушим `$mol_test_complete`, иначе бандл
завершит процесс раньше, чем мы начнём. Пауза перед стартом нужна затем же.
`writeSync(1, …)` вместо `console.log`, потому что вывод через консоль на выходе может не
долететь.

```js
// node trace.js bog/vmap/app/export/-/node.test.js
const path = process.argv[2]
const $ = require( require('path').resolve( path ) )

const all = $.$mol_test_all.slice()
const mocks = $.$mol_test_mocks.slice()

$.$mol_test_all = []
$.$$.$mol_test_complete = ()=> {}

const w = s => require('fs').writeSync( 1, s + '\n' )

setTimeout( async ()=> {

	let fails = 0

	for( const t of all ) {
		const ctx = Object.create( $.$$ )
		for( const m of mocks ) await m( ctx )
		try { await t( ctx ) } catch( e ) { fails++; w( 'FAIL  ' + t.name + '  ::  ' + e.message ) }
	}

	w( 'total ' + all.length + ', failed ' + fails )
	process.exit( 0 )

}, 1200 )
```

Прогон под таймаутом, потому что `timeout` на macOS нет:

```
( node trace.js <бандл> & pid=$!; ( sleep 240; kill -9 $pid 2>/dev/null ) & w=$!; \
	wait $pid; kill $w 2>/dev/null )
```

Мокки обязательно прогонять по каждому тесту: на них висит подмена `$giper_baza_land.sync()`
и преднагенерённые ключи, без них крипта уходит в промис вне фибры и тест умирает молча.

## Гочи, специфичные для Гипер Базы

Подробности в памяти проекта, здесь только то, что бьёт по тестам этого пака.

- **`remote_list()` в тестах запрещён.** Резолвит ссылки через статический `glob`, ждёт
  синка с мастером, которого в тестах нет, и подвисает навсегда. Читать поуны через
  `land.Pawn( Type ).Head( link.head() )` по `items()` того же ленда. По той же причине
  `atom_link.remote()` в тестах не читают — берут сырой `val()`.
- **Крипта только внутри фибры.** `give()`, `encrypted(true)`, захват ленда. Вне фибры
  промис-throw глотается и тест умирает молча.
- **Лимит на тест — одна секунда.** Таймаут летит в `unhandledRejection`, который
  `mol/report/handler` регистрирует и глотает.
- Лучше не написать тест и честно сказать, чем оставить висящий: висящий отравляет сборку
  всем, потому что `mam_build` гоняет `node.test.js` в пайплайне.
